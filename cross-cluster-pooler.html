跨叢集連線到 CNPG Pooler 的路由設計

用 wildcard 網域取代 ip:nodePort，讓 cluster A 的 client 連到 cluster B 中任意一個 PgBouncer Pooler —— 拓撲沒問題，但「用 nginx 依 SNI 分流 PostgreSQL」這個前提，在預設的 libpq 之下是不成立的。

Scope nginx stream · NGINX IC TransportServer · CNPG Pooler Date 2026-09-03

◆ 拓撲可行

DNS → cluster A nginx (L4) → cluster B ingress → pooler pod 這條鏈本身沒有結構性問題，也確實能避開 nodePort。CNPG Pooler 是普通的 Service，接得上。

■ 有一個會直接壞掉的前提

PostgreSQL 預設用 SSLRequest 做 STARTTLS，第一個封包不是 TLS ClientHello。nginx 的 ssl_preread 讀不到 SNI，wildcard 分流會全部落到 default backend。

▲ pgbouncer 改動很小

真正要動的是 client_tls_sslmode、憑證的 SAN，以及三層 idle timeout 與 TCP keepalive。連線池參數本身沿用原本的即可。

§1 為什麼 SNI 分流預設會失敗

這是整個設計唯一的技術阻斷點，其他都是設定細節。

你原本在同叢集內用 k8s DNS 連線，所以從來沒碰過這件事：PostgreSQL 的連線不是以 TLS 開場的。 libpq 先建立明文 TCP，送出一個 8 bytes 的 SSLRequest 封包，等 server 回一個 byte（S 或 N）， 才開始 TLS 握手。也就是說，SNI 出現在第二次往返，而 nginx ngx_stream_ssl_preread_module 只看第一個封包。

要讓 SNI 可用，只有兩條路：(a) 讓 client 第一個封包就送 ClientHello（PostgreSQL 17 的 sslnegotiation=direct，搭配 ALPN postgresql），或 (b) 在邊界換上一個懂 PostgreSQL 協定的代理， 由它代答 SSLRequest 之後再讀 SNI。§3 把這兩條路寫成完整方案。

要強調的是：這個限制與 TLS 在哪裡終止無關。就算讓 nginx 自己終止（listen ... ssl）， 它一樣是直接對首包做 TLS 握手，遇到 SSLRequest 照樣失敗。 真正的分界線是代理有沒有實作 PostgreSQL 的 SSLRequest 交涉：nginx 沒有，Traefik 有。

§2 修正後的資料路徑

左半段兩個方案完全共用；差異只在 cluster B 邊界那一跳，以及 TLS 在哪裡終止。

§3 兩個方案與取捨

選哪一個，取決於「你能不能規定 client 的 libpq 版本」。

以 B 為主線。 client 幾乎都是公司自家服務，「舊 driver 連不上」的風險比一般情況低， sslnegotiation=direct 在 libpq 17+、pgx v5、node-postgres 上都可用——所以 A 是站得住腳的選項。 但真正的差別在成本怎麼成長：A 的憑證管理與 reload 影響範圍會隨 pooler 數量線性上升， 而 pooler 數量正是會一直增加的東西；B 的成本是一次性的。

選 A 的前提是把實際用到的 driver 與版本盤得完（含 BI 工具、GUI client 這些不會 rebuild 的）， 並接受 wildcard 私鑰會掛進資料庫 namespace 的每一個 pod。詳細取捨見另一份〈跨叢集邊界方案選型〉。 兩者其實可以並存：Traefik 的 TCP router 同時支援 passthrough 與 termination，同一個 hostname 兩種 client 都能進。

§4 Cluster A：local nginx

關鍵設計：讓它盡可能笨，新增 pooler 時不要碰它。

需要編進 --with-stream（官方 nginx image 已內建）。因為所有租戶都指到同一個 cluster B 入口， cluster A 不需要任何 SNI 判斷——它只是把 TCP bytes 原封不動轉過去，SNI 由 cluster B 解析。

/etc/nginx/nginx.confcluster A
# stream 區塊與 http 同層，不是放在 http 裡面
stream {
    log_format pg '$remote_addr [$time_local] $status '
                  '$bytes_sent/$bytes_received $session_time';
    access_log /var/log/nginx/pg.log pg;

    upstream cluster_b_edge {
        # 列出所有 ingress 節點 / LB VIP；不要靠 DNS round-robin 當 HA
        server 10.20.0.11:5432 max_fails=3 fail_timeout=10s;
        server 10.20.0.12:5432 max_fails=3 fail_timeout=10s;
    }

    server {
        listen 5432;
        proxy_pass cluster_b_edge;

        proxy_connect_timeout   5s;
        proxy_timeout           1h;   # 預設只有 10m，會砍掉閒置的 DB 連線
        proxy_socket_keepalive  on;   # 對 upstream 開 TCP keepalive

        # 不要開 proxy_protocol —— pgbouncer 不支援，會被當成垃圾封包
    }
}

如果你之後想在 cluster A 就依 hostname 分流到不同的 cluster B（多後端叢集），才需要 ssl_preread—— 但那同樣受 §1 限制，只有在方案 A（direct TLS）下才會有值：

選用：多後端叢集時的 SNI 分流僅方案 A 有效
map $ssl_preread_server_name $pg_backend {
    ~^[a-z0-9-]+\.us\.db\.example\.com$   cluster_b_us;
    ~^[a-z0-9-]+\.eu\.db\.example\.com$   cluster_b_eu;
    default                               "";        # 空值 → 連線失敗，等同拒絕
}

server {
    listen 5432;
    ssl_preread on;
    proxy_pass $pg_backend;
    proxy_timeout 1h;
}

§5 Cluster B：邊界設定

兩個方案各給一份可以直接套的 CR。

方案 A — NGINX Ingress Controller TransportServer

先在 controller 加上 -enable-tls-passthrough。啟用後 passthrough listener 預設接管 443； 若 443 上已有大量 HTTPS Ingress，建議用 -tls-passthrough-port=5432 拉一個獨立 port，兩邊互不影響 （記得 controller Service 也要開這個 port）。

transportserver.yaml每個 pooler 一份
apiVersion: k8s.nginx.org/v1
kind: TransportServer
metadata:
  name: tenant1-pg
  namespace: tenant1
spec:
  listener:
    name: tls-passthrough          # 內建 listener，不需在 GlobalConfiguration 宣告
    protocol: TLS_PASSTHROUGH
  host: tenant1.db.example.com   # SNI 比對值；(listener, host) 必須全域唯一
  upstream:
    name: tenant1-pooler
    service: tenant1-pooler        # CNPG 建立的 Service 與 Pooler 同名
    port: 5432
    maxFails: 2
    failTimeout: 10s
  upstreamParameters:
    connectTimeout: 5s
    nextUpstreamTimeout: 10s
  sessionParameters:
    timeout: 60m                 # 預設 10m —— 一定要調大
  action:
    pass: tenant1-pooler
為什麼一定要 direct TLS

「TLS 在哪裡終止」和「TLS 用什麼方式開場」是兩件事，這個限制屬於後者。 就算改成讓 nginx 自己終止（listen ... ssl），它的語意也是「首批 bytes 就是 TLS record」，收到就交給 OpenSSL； 而一般 libpq 送來的是 00 00 00 08 04 D2 16 2F，首 byte 不是 0x16，握手當場失敗， client 端看到的是 server closed the connection unexpectedly。 此時 client 還在等那一個 byte 的 S，而 nginx 沒有回它的程式碼——不論終止或直通，nginx 只會說一種開場方式。

另外，libpq 的 direct 模式會強制檢查 server 有沒有選 ALPN postgresql（防 ALPN confusion）， 沒選就自己中斷。TLS passthrough 下這由 pgbouncer 負責，不用你操心；但若你自己架 nginx 終止 TLS，記得補上 ssl_alpn postgresql;。

方案 B — Traefik IngressRouteTCP

Traefik 會讀首包、辨識出 PostgreSQL 的 STARTTLS 交涉、回覆 S，然後才做 TLS 握手取得 SNI。 這正是 nginx 缺的那一塊。

traefik values.yaml（靜態設定）一次性
ports:
  postgres:
    port: 5432
    exposedPort: 5432
    protocol: TCP
    expose:
      default: true
ingressroutetcp.yaml每個 pooler 一份
apiVersion: traefik.io/v1alpha1
kind: IngressRouteTCP
metadata:
  name: tenant1-pg
  namespace: tenant1
spec:
  entryPoints: [postgres]
  routes:
    - match: HostSNI(`tenant1.db.example.com`)
      services:
        - name: tenant1-pooler
          port: 5432
  tls:
    secretName: db-wildcard-tls    # *.db.example.com，在邊界終止
    # passthrough: true  ← 若改成直通，client 端請用 sslmode=require
    #   （passthrough 下 verify-full 的語意會跟著憑證來源改變）
自建替代方案

若不想引入 Traefik，這個代理其實只有一百多行 Go：讀 8 bytes、比對 0x04D2162F、回一個 'S'、 用 tls.Server 拿 ClientHelloInfo.ServerName、查表撥到後端、再對後端重做一次 SSLRequest 交涉、雙向 io.Copy。 好處是路由表可以直接 watch Pooler CR，完全不用產生 ingress CR。

§6 Pooler / PgBouncer YAML 要改什麼

比你想像的少。連線池參數沿用，重點在 TLS 模式與 keepalive。

pooler.yamlCNPG
apiVersion: postgresql.cnpg.io/v1
kind: Pooler
metadata:
  name: tenant1-pooler              # Service 會用同一個名字
  namespace: tenant1
spec:
  cluster:
    name: tenant1-db
  instances: 3                      # 邊界會做 L4 負載平衡，多開幾個
  type: rw
  pgbouncer:
    poolMode: transaction           # 注意：prepared statement / advisory lock 的相容性
    parameters:
      client_tls_sslmode: "require"       # 方案 A 必填；方案 B 視內網政策
      max_client_conn: "1000"
      default_pool_size: "25"
      min_pool_size: "5"
      max_db_connections: "80"
      ignore_startup_parameters: "extra_float_digits,options"  # CNPG 要求保留這兩個

      # --- 跨叢集才需要的：讓死掉的 TCP session 被回收 ---
      tcp_keepalive: "1"
      tcp_keepidle: "30"
      tcp_keepintvl: "10"
      tcp_keepcnt: "3"
      client_idle_timeout: "0"             # 交給 nginx/LB 管，避免兩邊互踢
      server_idle_timeout: "600"
      server_lifetime: "3600"
      query_wait_timeout: "120"

      # --- 觀測性：因為 client IP 會被代理蓋掉（見 §8） ---
      application_name_add_host: "1"
      log_connections: "1"
      log_disconnections: "1"
  serviceTemplate:
    spec:
      type: ClusterIP              # 不需要 NodePort / LoadBalancer
三個必須知道的限制

1. [databases]、[users]、以及所有 server_tls_* / client_tls_cert_file 都由 operator 接管，寫了會被忽略或被 webhook 擋下。 可設定的 parameter 是一份白名單，請以你這版 CNPG 的 Connection pooling 文件為準。

2. Pooler 目前不能指定自己的憑證（CNPG issue #8672），它一律沿用 Cluster 的 server 憑證——這正好是 §7 的操作點。

3. 方案 A 的 direct TLS 需要 pgbouncer ≥ 1.25（client 端 direct TLS 支援）。CNPG 1.26 / 1.27 起新建的 Pooler 預設就是 1.25.1；舊叢集請確認 image tag。

連線數的算術

跨叢集之後 client 數量會失控成長，這兩條不等式要先算過：

  • instances × max_client_conn = 邊界代理要維持的最大並發 TCP session。3 × 1000 = 3000，nginx 沒問題，但雲端 LB 的每後端連線上限要確認。
  • instances × default_pool_size × (資料庫, 使用者) 組合數 必須 < PostgreSQL 的 max_connections 減掉 superuser_reserved_connections 與 CNPG 自己的連線。用 max_db_connections 設一個硬上限比較保險。

§7 憑證與 DNS

client 用 verify-full 時，憑證必須認得外部網域，而不是 k8s service 名稱。

CNPG 預設用自簽 CA 簽發 server 憑證，SAN 是 tenant1-db-rw.tenant1.svc 這類內部名稱。 外部 client 連 tenant1.db.example.com 時，verify-full 一定會失敗。兩種解法：

  • 方案 B（邊界終止）：把 wildcard 憑證放在邊界的 Secret，Cluster / Pooler 完全不用動。 用公開 CA 簽的話，client 端只要寫 sslmode=verify-full，連 sslrootcert 都不用給——做對的事反而最省事。
  • 方案 A（直通）則必須動 Cluster：pgbouncer 直接對外出示憑證，wildcard 憑證必須灌進去：
cluster.yaml僅方案 A 需要
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: tenant1-db
spec:
  certificates:
    serverTLSSecret: db-wildcard-tls   # *.db.example.com 的 tls.crt / tls.key
    serverCASecret:  db-wildcard-ca    # ca.crt

用 cert-manager 簽一張 *.db.example.com 即可。 所有 CNPG Cluster 在同一個 namespace 的話，Secret 就只有一份，每個 Cluster 的 serverTLSSecret 填同一個名字，輪替時原地續、一起生效——新增租戶時憑證這一環是零成本的。 （若改成一租戶一 namespace，才需要 reflector / kyverno 把 Secret 同步過去。） CNPG 的 operator 與 instance 之間只驗 CA、不驗 DNS name，所以換成外部憑證不會打斷內部通訊。

兩件要先確認的事

1. 輪替時 pooler 會不會自動載入新憑證。CNPG 對自簽憑證有處理輪替，但使用者提供的 Secret 更新後 pgbouncer 是否重載請先實測——不然問題會在 90 天後才出現。必要時在續期流程後加一次 pooler rollout。

2. wildcard 只涵蓋一層 label。*.db.example.com 能對上 tenant1.db.example.com，但對不上 pooler.tenant1.db.example.com。 hostname 命名規則要先定死。

DNS：一筆 *.db.example.com A → cluster A nginx 的 VIP 就夠了。 新增 pooler 不需要新增 DNS 記錄，這是這個設計相對 nodePort 最大的維運收益。

§8 會咬人的地方

這些不會在 PoC 出現，但會在上線兩週後出現。

  1. Client IP 全部變成代理的 IP丟掉的是網路來源，不是身分：SCRAM / 憑證認證照常運作，usename 準確。但 pg_hba 的 IP 規則與來源 IP 稽核會失效。注意這不是跨叢集造成的——只要走 PgBouncer，PostgreSQL 本來就看不到 client IP；跨叢集多丟的是 PgBouncer 自己 log 裡的那一層（現在看到的是 ingress pod IP）。追來源請靠：每個租戶一個 DB role、要求 client 帶 application_name、以及用 cluster A nginx 的 $remote_addr + SNI hostname + 時間戳做關聯。application_name_add_host 填的是 pgbouncer 看到的 client（= ingress pod），對追真實來源沒有幫助。PgBouncer 不支援 PROXY protocol，所以也無法把真實 IP 轉發進去。
  2. 三層 idle timeout 會互相打架cluster A nginx proxy_timeout（預設 10m）、cluster B sessionParameters.timeout（預設 10m）、以及雲端 LB 的 idle timeout（AWS NLB / GCP 常見 350s–600s）。三者都要 > 你的應用最長閒置時間，並且 client 端連線字串加上 keepalives=1 keepalives_idle=30 keepalives_interval=10，否則會出現典型的「連線看起來還在，一下 query 就 hang 住」。
  3. 每新增一個 pooler 就會 reload nginx新增 TransportServer 確實就是你要做的全部，reload 是資料面的副作用而非額外工作。開源 NGINX 沒有動態設定 API，controller 是「重產整份 nginx.conf → nginx -s reload」。舊 worker 會繼續服務既有連線，但不會無限等：worker_shutdown_timeout 到期就強制關閉（ingress-nginx 預設 240s）。真正的問題是 blast radius——改 tenant50 的 CR，掐斷的是 tenant1–49 正在跑的交易。請把 worker-shutdown-timeout 調到遠大於最長交易時間、批次套用 CR 不要一個一個發、並確認應用端有重連與 retry。Traefik 是 in-process 更新路由表，既有 TCP 連線不受影響，這是選 B 的另一個實質理由。
  4. pool_mode 的語意陷阱transaction 模式下 SET、advisory lock、部分 prepared statement 行為會變。跨叢集後你面對的是「一直有新 client 出現」，這些 client 不一定知道自己連的是 pooler。建議在使用文件裡直接寫明 pool mode，並考慮同時提供一個 session 模式的 pooler hostname 給有需要的人。
  5. 健康檢查只到 TCP 層nginx 的 max_fails 只看 TCP 連得上與否。PgBouncer 活著但後端 PostgreSQL 掛掉時，連線仍會被送進去然後失敗。要真的做應用層探測，需要 NGINX Plus 的 healthCheck 或在 pooler pod 上放一個能跑 SELECT 1 的 readiness probe。
  6. 租戶名稱與 hostname 的對應要有唯一性約束(listener, host) 在 NGINX IC 必須全域唯一，衝突時其中一個 CR 會被靜默拒絕。多對多場景下建議由一個 controller 或 Argo template 從 Pooler 名稱推導 hostname，不要讓人手寫。

§9 驗證步驟

照順序做，每一步都能把問題定位到某一跳。

由外而內逐跳驗證bash
# 1. DNS 與 L4 通不通（不涉及 PG 協定）
getent hosts tenant1.db.example.com
nc -vz tenant1.db.example.com 5432

# 2. 邊界認不認得 SNI —— 方案 A 用這個確認 ClientHello 有被讀到
openssl s_client -connect tenant1.db.example.com:5432 \
    -servername tenant1.db.example.com -alpn postgresql </dev/null 2>&1 \
  | grep -E 'subject=|ALPN|Verify return'

# 3. 一般 client（方案 B 的主要路徑）
psql "host=tenant1.db.example.com port=5432 dbname=app user=app \
      sslmode=verify-full sslrootcert=/etc/ssl/certs/ca.crt"

# 4. direct TLS client（方案 A，需要 psql 17+）
psql "host=tenant1.db.example.com port=5432 dbname=app user=app \
      sslmode=verify-full sslnegotiation=direct sslrootcert=/etc/ssl/certs/ca.crt"

# 5. 確認真的走到正確的 pooler、而且中間確實經過 pgbouncer
psql "..." -c "select current_database(), inet_server_addr(), pg_backend_pid();"
psql "..." -c "select application_name, client_addr from pg_stat_activity
               where pid = pg_backend_pid();"
#   application_name 會帶上 pgbouncer 加的 host 資訊；
#   client_addr 會是 pooler pod 的 IP，不是你的 IP —— 這是預期行為（見 §8）

# 6. 長連線存活測試：開著連線放 20 分鐘再下一個 query
psql "... keepalives=1 keepalives_idle=30 keepalives_interval=10" \
     -c "select pg_sleep(1200); select now();"

第 2 步若 openssl 拿不到憑證但第 3 步的 psql 可以，就確定你落在方案 B 的路徑上（代理有代答 STARTTLS）。 反之若第 4 步能連、第 3 步不能，就是純 passthrough 的方案 A，這時要回頭確認舊 client 的相容性。
