實作規格 · 分階段交付

pg-proxy 兩階段實作

這份文件只規劃 pg-proxy 這一個服務，是給實作者照著做的規格。 第一階段：終止 TLS、依 SNI 分流、記錄每一條連線、轉發到 Pooler，不做任何判斷。 第二階段：讀 Redis，做連線層的權限控制與撤銷。 第一階段有四個接縫現在就要留好，否則第二階段是重寫。

§0 範圍與交付目標

只做 pg-proxy。Redis 裡的資料由已經存在的中央服務維護，不在這份規劃裡。

  • 第一階段做完之後 所有 client 經 APISIX 連到 pg-proxy，再由 pg-proxy 轉到各 cluster 的 Pooler， client 端零改動。stdout 有每一條連線的 cluster / user / database / client_ip。 沒有任何連線會被拒絕。
  • 第二階段做完之後 中央服務在 Redis 把某個帳號的授權清空， 新連線立刻被擋、既有連線在十秒內斷開，被擋的連線也有稽核紀錄。 Redis 掛掉或資料不見時，資料庫連線不受影響（降級 + 告警）。
  • 不在這份規劃裡：中央服務那一側 誰把資料寫進 Redis、寫失敗怎麼補、資料從哪個表來——都是既有中央服務的事。 pg-proxy 只負責讀，而且必須在讀不到或讀到怪東西時安全地降級。 需要跟他們談定的只有 §7 那份讀取契約。
  • 不在這兩階段裡：SQL 語句層 記錄或攔截 SQL 需要持續解析訊息，雙向轉發的快路徑就此消失。那是之後的事（見 §10）。
建議的程式碼佈局接縫就是這些 package 的邊界
cmd/pg-proxy/main.go          # 組裝與設定

internal/proxy/               # listener、handleConn（§4 的十一步）
internal/pgwire/              # 首包判斷、StartupMessage、ErrorResponse
internal/route/               # 接縫 A Router
internal/authz/               # 接縫 B Authorizer：allowAll / redis
internal/registry/            # 接縫 C 連線登記表 + Sweep
internal/relay/               # 接縫 D Relay：copyRelay
internal/audit/               # 事件型別 + JSON sink

§1 整體架構

單一叢集。實線是第一階段就要有的，虛線是第二階段才加上去的。

§2 兩階段的分界

兩個階段動的是同一條連線的同一個位置。

那個位置是：TLS 握完、StartupMessage 讀完、還沒撥後端的那一瞬間。 第一階段在那裡把 user 與 database 寫進 log 就繼續往下走； 第二階段在同一個位置多問一次 Redis，然後決定要不要往下走。

所以第一階段必須解析 StartupMessage，只是解析完不做判斷。 多寫大約五十行，換來兩件事：log 裡有真實的帳號與資料庫 （第二階段要對帳的清單就靠它，見 §6）， 以及第二階段的插入點已經存在，不用回頭改連線流程。

§3 第一階段 · 範圍

把「不做什麼」寫得跟「做什麼」一樣清楚，否則範圍一定會漂。

  • 終止 TLS 讀首包的 8 bytes 判斷型別。對 SSLRequest 回 'S' 後用 wildcard 憑證握手；GSSENCRequest 回 'N'； CancelRequest 依 SNI 轉給對應 Pooler，不做其他事。
  • 依 SNI 分流 從握手拿到 hostname，查路由表得到 cluster 識別字與後端位址。 cluster 識別字第一階段只寫進 log，但現在就要有——第二階段拿它當 Redis 的 key。
  • 解析 StartupMessage 取出 user、database、application_name， 不做任何判斷，原樣轉給後端。
  • 記錄與轉發 登記連線、輸出 connect 事件、對後端做標準 PostgreSQL TLS 交涉、 雙向轉發位元組、結束時註銷並輸出 disconnect 事件。
  • 不做：任何權限判斷 沒有 Redis、沒有政策、沒有拒絕邏輯。所有連線一律放行。
  • 不做：startup 之後的訊息解析 轉發之後就不看內容了，所以沒有 SQL log。
第一階段的難度不在上面那四件事

核心邏輯大概兩百行。真正決定能不能上線的是周邊： graceful shutdown（SIGTERM 後停收新連線、等既有連線結束， terminationGracePeriodSeconds 要一起調大）、 憑證熱重載（tls.Config.GetCertificate 每次握手讀當前憑證， cert-manager 續期後不重啟就換上）、全域與每個 cluster 的連線上限、 後端故障與 idle timeout 的處理（idle timeout 要與 APISIX 及雲端 LB 對齊， 避免互踢）、metrics。這五項的工作量比核心邏輯大。

§4 第一階段 · 連線流程與協定細節

從 accept 到關閉，接縫的位置標在右邊。

handleConn 1. accept，設 TCP_NODELAY 與握手 deadline
2. 讀 8 bytes → 判斷首包型別
3. 回 'S'，TLS 握手 （憑證由 GetCertificate 動態取得）
4. Router.Lookup(sni) → cluster、後端位址 ← 接縫 A
5. 讀 StartupMessage → user、database、application_name
6. Authorizer.Check(...) → 第一階段永遠回 allow ← 接縫 B
7. 撥後端、標準 SSLRequest 交涉、原樣送出 StartupMessage
8. 雙向轉送認證訊息，等到 AuthenticationOk
9. Registry.Add(conn) 並輸出 connect 事件 ← 接縫 C
10. Relay.Run(client, backend) → 第一階段就是 io.Copy ← 接縫 D
11. defer：Registry.Remove 並輸出 disconnect 事件

第 6 步在第一階段是一個永遠回 allow 的空實作， 但它必須存在，而且必須在第 7 步之前。 第 8 步要等 AuthenticationOk 才登記連線，是因為在那之前 client 宣稱的 user 還沒被驗證——log 的可信度取決於它，現在就照這個順序寫。

首包的四種可能

前 8 bytes都是 big-endian int32
int32 length = 8   int32 80877103   → SSLRequest      回 'S' 然後握手
int32 length = 8   int32 80877104   → GSSENCRequest   回 'N'，client 會退回一般流程
int32 length = 16  int32 80877102   → CancelRequest   再讀 8 bytes（pid + secret）
int32 length = N   int32 196608     → 明文 StartupMessage（協定 3.0）

# StartupMessage 的 payload：以 \0 結尾的字串成對出現，最後多一個 \0
"user\0app_rw\0database\0orders\0application_name\0metabase\0\0"
CancelRequest 是最容易漏的一項

它走的是一條全新的 TCP 連線，沒有認證、沒有 user 欄位， 只帶要取消的後端 pid 與 secret key。但因為 TLS 已經終止，SNI 仍然告訴你要轉給哪個 Pooler—— 轉過去讓 PgBouncer 處理即可，不要套用任何後續流程（第二階段也不要對它做權限判斷， 它根本沒有身分可查，記一筆稽核事件就好）。 多副本也沒問題，落在哪個 replica 都能轉。 漏掉這一項的症狀是「查詢按 Ctrl-C 沒有反應」，而且通常到正式環境才發現。

對後端的連線

撥到 Pooler 之後走標準 PostgreSQL TLS 交涉：送 SSLRequest、 等 'S'、再握手。不要用 direct TLS——那會多帶一個 PgBouncer 1.25 以上的版本要求。 憑證用 CNPG operator 自簽的內部 CA 驗證即可，wildcard 憑證只存在於 pg-proxy 這一側。

ErrorResponse 的位元組格式

第一階段只有「後端連不上」會用到，但第二階段整個拒絕路徑都靠它，現在就寫好：

ErrorResponse寫完就關閉連線
'E'                    1 byte
int32 length           # 含自己，不含 type byte
'S' "FATAL" \0        # severity（會被本地化的舊欄位）
'V' "FATAL" \0        # severity（不本地化，PG 9.6+）
'C' "28000" \0        # SQLSTATE
'M' "..."   \0        # 給人看的訊息
\0                     # 欄位結束
SQLSTATE用在哪階段
08006後端連不上、後端握手失敗一
28000帳號沒有授權、要連的 database 沒有授權二
57P01撤銷既有連線（terminating connection due to administrator command）二
53300超過連線上限一

不要用靜默 RST 拒絕連線。client 端會變成難以診斷的逾時， 而 57P01 是 PostgreSQL 自己 pg_terminate_backend 用的同一個代碼， 各家驅動都認得，會走既有的重連或錯誤路徑。

§5 第一階段 · 四個接縫

留好這四個，第二階段是加實作；沒留好，是重寫。

A · Router

介面Lookup(sni) 回傳 cluster 識別字與後端位址
一階段從 Pooler 的 annotation 建路由表，informer 更新時整份 atomic 換掉。
二階段不變。
現在回傳值一定要包含 cluster 識別字， 不能只回後端位址。第二階段拿它組 Redis 的 key，第一階段拿它寫 log。

B · Authorizer

介面Check(cluster, user, db, ip) 回傳放行與否加原因
一階段allowAll，永遠回放行。
二階段換成查 Redis 的實作，加逾時、回退快取、降級、dryRun。
現在呼叫點要在 StartupMessage 解析完、撥後端之前。 放錯位置（例如撥完後端才檢查）第二階段會浪費一次後端連線，拒絕的錯誤訊息也會變得很難處理。

C · Registry

介面Add / Remove / Snapshot / Count
一階段graceful drain 與連線上限要用它。
二階段多一個每 10 秒的 Sweep，重驗後撤銷。
現在不能只存一個計數。要存得下每條連線的 cluster、user、database、conn_id 與兩側 socket，而且要能列舉。 第二階段的撤銷掃描完全靠它。

D · Relay

介面Run(client, backend)
一階段io.Copy 雙向，直到任一端關閉。
之後換成訊息解析迴圈（SQL 稽核那一版，不在這兩階段）。
現在把 io.Copy 收在介面後面就好。 連線管理、逾時、關閉順序留在外圍，之後換實作時這些都不用動。
還有一個不是介面的接縫

連線的 struct 現在就把欄位帶齊： conn_id、cluster、sni、client_ip、 user、database、application_name、 backend、started_at， 以及一個預留的 revoked 布林欄位（第二階段的撤銷會標記它）。 第一階段用不到全部，但第二階段的稽核事件與撤銷掃描要的就是這些。 現在補齊是零成本，之後補是每個地方都要改。

§6 第一階段 · log、設定與驗收

log 不只是觀測，它是第二階段能不能安全切換的依據。

兩種事件

stdout · JSON 一行一筆同一個 conn_id 串起整條連線
{"ts":"2026-09-09T10:58:03.220Z","event":"connect","conn_id":"01K5R7Q2XJ",
 "cluster":"tenant1","sni":"tenant1.db.example.com","client_ip":"10.42.7.19",
 "user":"analyst_ro","database":"orders","application_name":"metabase",
 "backend":"tenant1-pooler.cnpg.svc:5432","tls":"TLSv1.3","handshake_ms":3.1}

{"ts":"2026-09-09T11:04:19.006Z","event":"disconnect","conn_id":"01K5R7Q2XJ",
 "reason":"client_close","bytes_in":18422,"bytes_out":9931204,"duration_s":375.8}

reason 的值：client_close / backend_close / backend_error / idle_timeout / shutdown （第二階段多一個 policy_revoked）。

這份 log 是交給中央服務那邊的東西

第一階段最有價值的產物是「實際上有哪些帳號在連哪個資料庫」的真實清單。 pg-proxy 不負責把它寫進 Redis，但要負責把它整理成可以直接對帳的形狀交出去—— 中央服務那邊拿它跟申請紀錄比對，補齊之後再寫進 Redis。 沒有這一步，第二階段開強制的那一刻會有一批人一起斷線。

從 log 整理出實際使用情形交給中央服務對帳
jq -sr '
  map(select(.event == "connect"))
  | group_by(.cluster + " " + .user)
  | map({ cluster: .[0].cluster,
          user:    .[0].user,
          dbs:     (map(.database) | unique) })
' proxy.log

# 輸出：
[{"cluster":"tenant1","user":"app_rw","dbs":["orders"]},
 {"cluster":"tenant1","user":"analyst_ro","dbs":["orders","reports"]},
 {"cluster":"tenant2","user":"app_rw","dbs":["billing"]}]

觀測期至少要跨過一次月結——只跑一週很可能漏掉月初才跑的批次帳號。

驗收

  • 相容性
    各家驅動都要實測 psql（sslmode 從 require 到 verify-full）、 JDBC、pgx、asyncpg、psycopg，以及你們實際在用的 ORM。 重點不是「能連」，是連線池的建立與回收行為正常。
  • 大流量
    COPY 與 pg_dump COPY FROM STDIN 灌一個大檔、pg_dump 匯出一個大庫。 緩衝區大小、記憶體用量，以及有沒有哪個逾時會在中途踢掉連線，要親眼看過。
  • 中斷
    query cancel 跑一個長查詢然後按 Ctrl-C，要真的取消。見 §4 的 CancelRequest。
  • 部署
    rollout 不能斷既有連線 在有長連線的情況下滾動更新一次。SIGTERM 之後要停收新連線、等既有連線自然結束； terminationGracePeriodSeconds 沒調大的話這一項一定失敗。
  • 憑證
    輪替不重啟、不斷線 手動觸發一次 cert-manager 續期，確認新連線用到新憑證、既有連線不受影響。
  • log
    每一條連線都要有 user 和 database 抽樣比對：同一段時間內 connect 事件的數量與 pg_stat_activity 對得起來，而且沒有 user 是空的。 這一項不過，第二階段就沒有可信的輸入。

§7 第二階段 · pg-proxy 讀什麼

這是對外部的讀取契約，不是資料的設計。要跟中央服務那邊談定的就這一節。

pg-proxy 只需要回答一個問題：這個帳號能不能連這個 database。 所以它讀的形狀就照著這句話長——一個 cluster 一個 HASH， field 是帳號名稱，value 是它能連的 database 清單。

Redis · pg-proxy 只讀不寫一個 cluster 一個 key
pgproxy:policy:tenant1    HASH
    app_rw         ["orders"]
    analyst_ro     ["orders","reports"]
    batch_job      ["orders","logs"]

pgproxy:policy:tenant2    HASH
    app_rw         ["billing"]     # 跟 tenant1 的 app_rw 無關
  • key 的 {cluster} 用中央服務自己已經在用的 cluster 識別字。pg-proxy 從 SNI 查路由表就有了 （接縫 A 的回傳值），對方不必知道任何 DNS 名稱。
  • field 是帳號名稱 就是連線字串裡的 user，也就是 StartupMessage 送過來的那個字串， 一字不差。同一個 cluster 內帳號不重複，所以不會衝突； 不同 cluster 的同名帳號是不同的人，所以 key 必須按 cluster 切。
  • value 是 database 名稱的 JSON 陣列 每條新連線會解一次，所以保持小。之後要加連線數上限之類的， 把陣列換成 {"databases":[...],"maxConnections":40} 即可，key 結構不用動。
  • 停用要寫空清單 []，不要 HDEL 這是唯一需要對方配合的一件事。HDEL 之後 pg-proxy 讀到的是 nil，而 nil 也可能是「Redis 被 flush」或「key 被淘汰」—— 分不出來。寫一個空清單就只有一個意思。 而且開通、改權限、停用都變成同一行 HSET，對方的程式碼不用分岔。
pg-proxy 對這份資料的立場

它只讀，而且必須假設隨時可能讀不到或讀到怪東西。 Redis 掛了、被 flush、key 被 maxmemory 淘汰、value 寫壞—— 這四種情況 pg-proxy 都得安全地處理（§8）。 資料是不是最新的、寫失敗有沒有補，是中央服務那一側的責任，pg-proxy 管不到也不該管。

順帶一個要請他們確認的 Redis 設定： maxmemory-policy 不能是 allkeys-lru。 跟一般快取共用實例的話，記憶體壓力下政策 key 會被默默淘汰， 症狀是「某個 cluster 的人整批連不上」。

§8 第二階段 · 閘門與撤銷

全部都在 pg-proxy 裡面，動到的只有接縫 B 和接縫 C。

接縫 B：Redis 版的 Authorizer

一次 pipeline 送兩個指令：HLEN 判斷這個 cluster 的資料還在不在， HMGET 取那個帳號的授權。兩個都要，缺一個就會把 「Redis 資料不見了」誤判成「這些人都沒有授權」。

閘門 ①一次往返，兩個指令
key := "pgproxy:policy:" + cluster
pipe := rdb.Pipeline()
lenCmd := pipe.HLen(ctx, key)
getCmd := pipe.HMGet(ctx, key, user)   // 用 HMGet 不要用 HGet：
_, err := pipe.Exec(ctx)               // HGet 的 redis.Nil 會讓 Exec 回錯誤

if err != nil {
    return fallback(cluster, user, db)   // 逾時或連不上
}
if lenCmd.Val() == 0 {
    return degraded(cluster, user, db)   // 整個 HASH 沒了 → 絕不當拒絕
}

raw := getCmd.Val()[0]
if raw == nil {
    return deny("28000", "no grant for this account")
}
var dbs []string
if json.Unmarshal([]byte(raw.(string)), &dbs) != nil {
    return degraded(cluster, user, db)   // 資料壞掉也不能當拒絕
}
if !slices.Contains(dbs, db) {
    return deny("28000", "database not granted: "+db)
}
cache.Store(cluster, user, dbs)                // 供 fallback 使用
return allow()
Redis 回什麼意思怎麼處理
HLEN > 0，欄位有值正常看清單裡有沒有那個 database
HLEN > 0，欄位 nil這個人真的沒申請過deny 28000
HLEN = 0整個 HASH 沒了，資料不可信絕不當拒絕：回退快取 + 告警
逾時 / 連線錯誤Redis 抖動或掛了回退快取 + 告警
值不是合法 JSON寫壞了回退快取 + 告警

回退快取是一份「每個 (cluster, user) 上次成功的答案」， 只在上面後三種情況才使用，並帶一個存活上限（例如 5 分鐘）；超過上限就進降級策略。 降級策略要是一個明確的設定項（degradeAction: allow | deny）， 預設 allow 並告警——把它設成 deny 等於讓一次 Redis 抖動變成全叢集的資料庫故障。

Redis 的逾時要設得很緊（例如 100ms）。沒有逾時的話 Redis 一卡住， 新連線就無限期地掛在那裡——比拒絕還糟，因為 client 看到的是逾時而不是錯誤訊息。 連線建立的速率不是問題：連線池會把連線握著，真正的尖峰是部署或擴容時的重連風暴， 那個量級 Redis 完全吃得下。

接縫 C：定期重驗

撤銷既有連線不需要算政策差集。你手上已經有連線登記表， 每 10 秒把裡面的連線批次拿去 Redis 重驗一次就好：

Registry.Sweep — 每 10 秒 1. Snapshot() 取出所有連線，依 cluster 分組
2. 每個 cluster 一次 pipeline：HLEN + HMGET（該組所有 user，去重）
3. HLEN 為 0 或查詢失敗 → 整輪跳過，告警。不要砍任何連線
4. 對每條不再合格的連線：標記 revoked、送 FATAL 57P01
5. 關閉 client 與 backend 兩側 socket（不關後端會留下孤兒）
6. 輸出 disconnect 事件，reason: policy_revoked

第 3 步是這一段最重要的一行。掃描出錯時的正確行為是什麼都不做—— 一次 Redis 故障把所有連線砍光，比撤銷晚十秒嚴重得多。

幾千條連線用 pipeline 分批，幾個 RTT 就結束。 既有連線的撤銷延遲就等於這個間隔，10 秒是合理起點。

被擋掉的 client 會立刻重連

大多數連線池吃到 FATAL 會馬上重試。閘門 ① 一定要跟撤銷同時生效， 否則會變成「砍掉→重連→再砍」的迴圈，稽核 log 會被灌爆。 可以考慮對短時間內被拒絕多次的來源加一點退避。

多一種稽核事件

stdout第二階段唯一新增的事件型別
{"ts":"2026-09-09T11:06:02.771Z","event":"auth","conn_id":"01K5R8M4TQ",
 "cluster":"tenant1","client_ip":"10.42.7.19","user":"analyst_ro","database":"orders",

§9 第二階段 · 上線程序與驗收

不要直接開強制。先跑觀察模式，把數字跑到 0。

  • 步驟一
    開 dryRun authz.enabled: true 但 authz.dryRun: true—— 照常查 Redis、照常記錄「這條連線會被擋」，但一律放行。 對連線行為零影響，可以放心開在正式環境。
  • 步驟二
    盯 would_deny pgproxy_authz_would_deny_total 每出現一個新的 (cluster, user)，就是 Redis 裡漏掉的一筆授權，回報給中央服務那邊補。 跑到連續數天為 0——不是「大致上沒問題」，是 0。 這一段建議也跨過一次月結。
  • 步驟三
    先做故障演練，再關 dryRun 下面三項演練在 dryRun 期間就要做完。確認降級行為正確之後， 再逐個 cluster 把 dryRun 關掉，不要一次全開。

驗收 · 功能

  • 撤銷
    把某個帳號的授權清空 Redis 寫入 [] 之後：新連線立刻被擋並收到清楚的錯誤訊息； 既有連線在一個掃描間隔內斷開，disconnect 事件的 reason 是 policy_revoked；後端那一側的連線也確實關掉了 （去 pg_stat_activity 確認，不要只看 client 端）。
  • 授權範圍
    沒授權的 database 用一個只被授權 orders 的帳號去連 reports，要被擋， 而且錯誤訊息說得出是哪一個資料庫沒有授權。
  • 重連風暴
    擋掉一個有連線池的帳號 應用程式會立刻重連。確認 auth 事件的量在可接受範圍內、 退避有生效、CPU 沒有被拒絕路徑吃掉。

驗收 · 故障演練（比功能重要）

  • 演練
    把 Redis 停掉 新連線仍然要能建立（走回退快取或降級），並且告警。 如果結果是「所有人連不上」，代表逾時或 degradeAction 沒設對—— 那會把一次 Redis 抖動放大成全叢集的資料庫故障。
  • 演練
    FLUSHDB 在測試環境清空 Redis。HLEN 變成 0，所以 pg-proxy 必須 拒絕把找不到解讀成拒絕：新連線走降級、 而且撤銷掃描要整輪跳過、一條連線都不能砍。 這一項沒演練過就上線，等於埋了一顆隨時會炸的雷。
  • 演練
    讓 Redis 變慢 注入延遲（例如 500ms）。確認 redis.timeout 有生效、 新連線走回退快取而不是卡住，並且 pgproxy_redis_latency_seconds 看得出來。 「慢」比「掛掉」更常見，也更難發現。

§10 範圍外

先寫下來，之後才不會被當成「你不是說會做嗎」。

中央服務那一側（既有系統，不在這份規劃裡）

  • 誰把資料寫進 Redis、寫失敗怎麼補 pg-proxy 只讀。資料是不是最新的、雙寫有沒有漏，是那一側的責任。 pg-proxy 這邊唯一的回應方式是安全降級（§8）與把 would_deny 回報出去（§9）。
  • 資料的正確性與新鮮度 pg-proxy 沒有辦法判斷 Redis 裡的資料是不是過期的。 如果需要這個能力，要請他們在每個 HASH 多寫一個同步時間戳欄位， pg-proxy 才能曝一個 policy_age_seconds。現在先不做。
  • 緊急封鎖的專用通道 要在中央服務之外另外擋人，需要一組他們不會覆寫的欄位。 要不要做是他們那邊的決定，pg-proxy 這邊只是多讀一個欄位。先不做。

pg-proxy 之後才做的

  • SQL 稽核 要記錄「誰執行了什麼 SQL」必須持續解析訊息，雙向轉發的快路徑就此消失。 那是接縫 D 換實作的那一版。第二階段做完能回答的是「誰在什麼時候連了哪個庫」。
  • 語句層的攔截 「這個帳號只能讀不能寫」不要用 SQL 文字判斷，太容易繞過。 正確做法是後端給一個唯讀的 PostgreSQL role，讓資料庫去擋。
  • row / column 層的權限 pg-proxy 擋的是連線，不是資料。GRANT 與 RLS 仍然是最後一道， 不能因為有了 proxy 就放鬆。
兩個已知的限制

來源 IP 會被改寫。PgBouncer 不支援 PROXY protocol， 所以 PostgreSQL 看到的仍是 pooler pod 的 IP。pg-proxy 的 log 記得下真實 client IP （前提是 APISIX 有把 PROXY protocol 帶過來），兩邊靠 conn_id 關聯。 SCRAM channel binding 不能用。TLS 在 proxy 終止、對後端重建， 綁定值兩段不同，client 設 channel_binding=require 會失敗。 預設值 prefer 沒問題，但要先確認沒有團隊把它設成 require。
