決策文件 · 跨叢集 CNPG Pooler 入口

方案 A 或方案 B

公司內部跨叢集：Cluster A 的應用服務要連到 Cluster B 的 CNPG Pooler， 用 wildcard 網域取代 ip:nodePort。差別只在 Cluster B 邊界怎麼處理那一次 TLS 開場， 而這個選擇會決定往後每新增一個 pooler 要付多少維運成本。

B建議

選 B：在邊界放一個懂 PostgreSQL 協定的代理

兩個前提讓 A 比一開始看起來更有競爭力：client 幾乎都是自家服務（相容性風險低）， 而且所有 CNPG Cluster 在同一個 namespace（憑證只有一份，沒有跨 namespace 同步的問題）。 A 是站得住腳的選項。

建議仍是 B，但只剩一個決定性理由：nginx 每套用一份 CR 就 reload，會打斷其他租戶正在跑的交易， 而這個代價隨 pooler 的建立頻率累積。如果你們是自動化按需開通 pooler，B 值得那一個元件的成本； 如果建立頻率其實不高（一週幾個、人工觸發），把 worker-shutdown-timeout 調大就壓得住，那該選 A。

八個面向中 B 佔六項、A 佔兩項，但權重極不平均： 內部場景讓「Client 相容性」降權，單一 namespace 讓「憑證管理」降權， 只剩 「新增 pooler 的影響範圍」 是決定性的。完整對照見 §6。

§1 兩個方案長什麼樣

左半段完全相同，差別只有邊界那一跳——以及 TLS 從哪裡開始、到哪裡結束。

兩者的 wildcard DNS、Cluster A 的 nginx 設定、以及 Pooler 本身的連線池參數都一樣。 真正要選的只有一件事：Cluster B 邊界要不要解密——而這個選擇會連帶決定 client 端的版本門檻、憑證放哪， 以及新增一個 pooler 時會不會影響到其他租戶。

Driver 支援現況

方案 A 需要的 sslnegotiation=direct 支援度比想像中好，但仍有缺口： libpq 17+（psql、psycopg）、pgx v5（Go）、node-postgres 都已支援； Rust 的 sqlx 到目前為止還沒有（issue #3880 仍開著）， pgjdbc、asyncpg 等要看你實際用的版本。真正的問題不是「服務是不是我們自己的」，而是用什麼 driver、版本能不能鎖住。 另外別忘了不是應用服務的那些：BI 工具、GUI client、Grafana datasource——它們內嵌的 driver 通常最舊、也最難升。

§2 決策路徑

前兩題把大部分情況排除掉；你的場景會走到最後一格。

§3 什麼情況該重新考慮 A

以下任一條成立，上面的建議就要重新評估——你的場景裡第二、三條都值得認真看。

觸發條件 01

合規要求端到端加密

PCI-DSS、金融內控或客戶合約明文要求 payload 不得在資料庫以外的節點解密。 這是 A 唯一無法被取代的優勢——B 再怎麼配 mesh，邊界仍然握有私鑰。

觸發條件 02

Driver 清單盤得完

這一條你已經接近成立了。但「服務是自家的」不等於「driver 支援 direct TLS」—— 要盤的是實際用到的 driver 與版本，包含 BI 工具和 GUI client 那些你不會 rebuild 的東西。 盤得完而且鎖得住，A 的相容性風險就趨近於零。

觸發條件 03

不允許再引入邊界元件

組織政策或人力限制，不接受再多一個要值班的 ingress——內部平台團隊常有這個約束， 這一條的份量在你的場景裡比一般情況重。選 A 的話務必把 worker-shutdown-timeout 調大並批次套用 CR， 否則 §6 那個 reload 問題會直接吃掉省下來的維運成本。

§4 不必二選一

兩個 port、同一批 pooler，可以同時提供。

Traefik 的 TCP router 兩種模式都支援。開兩個 entrypoint 指到同一批 pooler： 5432 走終止服務所有 client，5433 走 passthrough給需要端到端加密的那幾個。 兩條路共用同一組 wildcard DNS 和同一批 IngressRouteTCP，維運成本幾乎不變。

traefik values.yaml混合模式
ports:
  postgres:            # 終止 TLS：相容所有 client
    port: 5432
    exposedPort: 5432
  postgres-e2e:        # passthrough：需 libpq ≥ 17
    port: 5433
    exposedPort: 5433
改變主意的成本很低

這不是一道單向門。A 和 B 之間切換，client 的連線字串不用改——hostname 和 port 一樣， 改的只有邊界設定和憑證放哪。真正會卡住的只有一件事：如果先選了 A、憑證已經灌進每個 Cluster， 退回 B 時要記得把 Cluster 上的 serverTLSSecret 收回來， 否則 wildcard 私鑰會繼續掛在資料庫 namespace 的每一個 pod 裡。

§5 選定 B 之後的三件事

這些不做，B 的優勢會被自己的設定抵消掉。

  • 補上邊界到 pooler 的保護。這是 B 唯一的實質弱點。最低限度是 NetworkPolicy 限制只有 Traefik 的 pod 能連 pooler service； 有 mesh 的話直接讓那一段走 mTLS。
  • wildcard 憑證用公開 CA 簽。這樣 client 端只要寫 sslmode=verify-full， 連 sslrootcert 都不用發給對方——做對的事反而變成最省事的路。
  • hostname 由程式推導，不要人工填。多對多場景下租戶名稱和 SNI 的對應一旦衝突， 其中一份 CR 會被靜默拒絕。用 controller 或 Argo template 從 Pooler 名稱生成。
先驗證再決定

下結論之前建議先花半天做兩件事：一是把公司實際在用的 driver 與版本盤一遍 （含 BI 工具、GUI client、Grafana datasource 這些不會 rebuild 的），這決定 A 到底可不可行； 二是拿其中最舊的那個 driver 對 Traefik 的 TCP router 連一次，確認 STARTTLS 代答在它身上真的成立。 第二件事是整個建議唯一依賴的假設。

§6 逐項對照

每一列都是一個實際會發生的情境，不是形容詞。

方案 ATLS 直通 · passthrough
方案 B協定感知代理 · Traefik
Client 相容性內部場景降權
連線字串要加 sslnegotiation=direct，且 driver 要夠新。 libpq 17+、pgx v5、node-postgres 都可以；Rust sqlx 目前還不行，BI / GUI 工具內嵌的 driver 通常最舊。 服務是自家的能大幅降低這個風險，但每個新接進來的 client 仍要確認一次。
優勢任何版本都可以，client 端就是最普通的 sslmode=verify-full。使用文件寫一次就結束。
失敗訊息支援成本
舊 client 拿到的是 server closed the connection unexpectedly—— 完全指向錯的方向，對方會先去查自己的網路和防火牆。
優勢正常的 TLS / 認證錯誤訊息，對方自己看得懂， 不會變成你的 ticket。
加密範圍資安
優勢client 到 pgbouncer 端到端加密， 邊界既不持有私鑰、也解不開 payload。
TLS 在邊界終止，邊界到 pooler pod 那一段是明文， 要靠 NetworkPolicy 或 service mesh 補回來。
憑證管理單一 NS 下降權
Cluster spec 要填 serverTLSSecret——但所有 Cluster 同一個 namespace 時 Secret 只有一份，沒有跨 namespace 同步問題，成本接近零。 待驗證：續憑證後 pooler 會不會自動載入。
優勢邊界一個 Secret，Cluster 完全不用動。 差別只剩私鑰住在哪：A 之下它掛進資料庫 namespace 的每一個 pod，B 之下只在 ingress 側。
新增元件維運
優勢沿用現有的 NGINX Ingress Controller， 只多開一個 -enable-tls-passthrough。
多一個 Traefik（或約 150 行的自寫 proxy）要部署、升版、監控、值班。
新增 pooler 的影響範圍決定性
每套用一份 CR 就觸發 nginx reload。舊 worker 在 worker_shutdown_timeout（ingress-nginx 預設 240s）後被強制關閉—— 新增 tenant50，斷的是 tenant1–49 正在跑的交易。
優勢in-process 更新路由表， 既有 TCP 連線不受影響。「不斷有新 pooler」正是這個差異會放大的場景。
邊界可觀測性除錯
純 bytes 轉送，log 只有 SNI、連線數、傳輸量。 握手為什麼失敗，邊界一無所知。
優勢邊界持有憑證， 能記錄 TLS 版本、憑證錯誤、握手失敗原因——問題出在哪一跳查得出來。
版本相依落在哪核心差異
libpq ≥ 17（client 側，你控制不了）、 pgbouncer ≥ 1.25、NGINX IC 要開 passthrough。
優勢Traefik ≥ 2.4 （平台側，你控制得了）。client 側零要求。
