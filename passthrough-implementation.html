Pooler TLS 直通架構

Cluster A 的服務經由 wildcard 網域連到 Cluster B 的 CNPG Pooler， TLS 在 Cluster B 邊界不終止，由 PgBouncer 完成握手。本文說明架構、TLS 不在邊界終止的原因，以及需要處理的問題；設定檔見另一份〈TLS 直通設定清單〉。文末列出改用 Traefik 時這些問題的變化。

元件 nginx stream · NGINX IC TransportServer · CNPG Pooler 日期 2026-09-03

§1 架構

四個節點、兩個叢集。TLS 從 client 一路加密到 PgBouncer，中途沒有任何節點解密。

DNS 只需要一筆 *.db.example.com 指向 Cluster A 的 nginx VIP。 每個 pooler 對應一個 hostname，新增 pooler 時只需要在 Cluster B 建立一份 TransportServer。

§2 TLS 為什麼不在邊界終止

終止 TLS，代表邊界要自己跟 client 完成 TLS 握手、把內容解開。PostgreSQL 的連線流程讓這件事在 NGINX IC 上有兩個障礙。

障礙一：PostgreSQL 不是一連上就開始 TLS

大部分人對 TLS 的印象來自 HTTPS：連上去，第一件事就是握手。PostgreSQL 不是這樣。 它先用明文問一句「你支援 TLS 嗎」，等對方回答之後，才開始握手。

PostgreSQL 一般連線流程 client → 你支援 TLS 嗎？ (SSLRequest，8 bytes)
server → 支援 (回 1 個 byte：S)
────────── 到這裡才開始 TLS 握手 ──────────
client → ClientHello …

問題就在這一句問話。當 nginx 設定成終止 TLS（listen ... ssl）， 它預期第一批收到的 bytes 就是 TLS 握手，收到後直接交給 OpenSSL 處理。 但實際收到的是那句問話，格式完全對不上，握手當場失敗、連線中斷。

nginx 終止 TLS 時收到的東西 預期 16 03 01 … ← TLS 握手的開頭
實收 00 00 00 08 04 D2 16 2F ← PostgreSQL 那句問話

而 client 此時還在等那個 S。nginx 沒有「回一個 S」的能力——它不認得 PostgreSQL 協定， 這不是設定問題，是功能不存在。

繞過方式：讓 client 跳過那句問話

PostgreSQL 17 的 libpq 加了 sslnegotiation=direct：一連上就直接開始 TLS 握手， 跟 HTTPS 一樣，不再先問。這樣 nginx 就看得懂了。但這個做法帶出第二個障礙。

障礙二：ALPN

原本那句「你支援 TLS 嗎 / 支援」的一問一答，除了協商加密之外還順帶做了一件事： 證明了對面確實是一台 PostgreSQL server。跳過之後，這個證明就沒有了—— client 一連上就握手，無從得知對面是 PostgreSQL 還是別的 TLS 服務（例如 SNI 打錯、或代理把它接到某個 HTTPS endpoint）。

所以 PostgreSQL 17 用 ALPN 補上這個證明。ALPN 是 TLS 握手裡本來就有的一個欄位， HTTPS 用它來談要用 HTTP/2 還是 HTTP/1.1；PostgreSQL 註冊的值是 postgresql。 在 direct 模式下，server 必須在握手時回答「我是 postgresql」，沒回答 client 就自己掛斷。

direct 模式（PostgreSQL 17） client → ClientHello (ALPN: postgresql)
server → ServerHello (ALPN: postgresql) ← 必須回這個
────────── 沒回 ──────────
server → ServerHello (ALPN: 無)
client → 主動中斷連線

這是 PostgreSQL 17 的規範，不能關閉。而 HTTPS 之所以從來不會遇到， 是因為 ALPN 對 HTTP 是選用的：server 不回，client 就退回 HTTP/1.1 繼續連，不報錯。

nginx 的 stream 模組本身有 ssl_alpn 指令（需 nginx ≥ 1.21.4）， 但 NGINX Ingress Controller 的 TransportServer 設定模板在 TLS 終止時 只產生 ssl_certificate 與 ssl_certificate_key，不產生 ssl_alpn。

直通為什麼沒有這兩個障礙

直通模式下邊界完全不參與 TLS：它只從 ClientHello 裡讀出 SNI（也就是 hostname）， 照著轉發原始 bytes，不解密、不回應任何東西。握手是 client 跟 PgBouncer 直接完成的。

所以障礙一不存在（邊界沒有要握手），障礙二也由 PgBouncer 承擔—— PgBouncer 1.25 加入 client 端 direct TLS 支援時，已一併設定 ALPN postgresql。

四種組合的結果

做法Client 首包邊界行為結果
邊界終止 · client 用一般 sslmode=require SSLRequest 對首包執行 TLS 握手 失敗 首 byte 非 TLS record，連線中斷
邊界終止 · client 用 sslnegotiation=direct ClientHello 握手成功，但未回應 ALPN 失敗 libpq 檢查 ALPN 後自行中斷
邊界終止 · 以 serverSnippets 補上 ssl_alpn postgresql; ClientHello 回應 ALPN postgresql 條件成立 需 controller 開啟 -enable-snippets；且 TLS 終止模式下的 SNI 路由支援視 NIC 版本而定
TLS 直通 · 本文採用 ClientHello 只讀取 SNI，不執行握手 可行 握手與 ALPN 由 PgBouncer 完成（需 ≥ 1.25）

關於 -enable-snippets

上表第三列需要在 controller 開啟 -enable-snippets。此 flag 預設關閉， 原因是 snippet 的內容是未經驗證的原始 nginx 設定，會直接注入共用的 nginx.conf。已知的影響有四項：

  • 權限範圍——能建立或修改該 controller 的 TransportServer / VirtualServer / Ingress 的人， 即可注入任意 nginx 設定。F5 的安全文件指出，snippet 可以讓 nginx 送出用於 TLS termination 的憑證與私鑰。 ingress-nginx 曾有對應的 CVE-2021-25742：能建立 Ingress 的低權限使用者可藉此取得 controller 的 service account token 與全叢集所有 namespace 的 secret。本質是一個 namespace 級的資源可以影響叢集級的設定。
  • 設定錯誤的影響範圍——snippet 不經 CRD schema 驗證。內容有誤會產生無效的 nginx.conf， reload 失敗後 nginx 繼續使用舊設定，該 controller 上所有人的設定變更都停止套用， 且不一定有明顯的錯誤回報。
  • 繞過 controller 的檢查——以 snippet 寫入的設定不受 controller 的衝突偵測保護， 例如 P14 的 (listener, host) 唯一性、重複的 listen 或衝突的 server_name。
  • 升級——snippet 插入的是產生出來的模板。NIC 升版後模板變動， 可能使 snippet 落在不同的 context 或與新產生的指令衝突。F5 將 snippets 列為進階功能， 由此產生的問題不在支援範圍內。

-enable-snippets 是全域 flag，沒有 per-namespace 開關， 實際的控制點是 RBAC——限制誰能建立或修改該 controller 的資源。 若依 P5 為 DB 流量部署獨立的 NIC 實例，可只在該實例開啟 snippets、主 HTTP controller 維持關閉； 該實例上僅有平台團隊管理的 TransportServer，上述第一、二項的影響範圍即限縮在 DB 流量之內。 更嚴格的做法是以 Kyverno 或 Gatekeeper 將 snippet 內容限制為允許清單 （例如只准出現 ssl_alpn 與 ssl_protocols）。

§3 需要注意的問題

依處理時機分為三組。每項列出症狀與處理方式。

上線前必須解決未處理則無法運作

  1. P1

    PgBouncer 版本

    症狀
    直通模式下 TLS 握手與 ALPN 由 PgBouncer 負責。版本低於 1.25 不支援 client 端 direct TLS，所有連線在握手階段失敗。
    處理
    確認 Pooler pod 的 image tag。CNPG 1.26 / 1.27 起新建的 Pooler 預設 1.25.1，既有 Pooler 不會自動升級。
  2. P2

    連線方的程式套件必須支援 direct TLS

    症狀
    這項要求落在連線方的應用程式上，不是平台端能設定或繞過的： 每個要連進來的服務，其專案相依裡的 PostgreSQL driver 套件本身必須支援 sslnegotiation=direct，且版本要夠新。套件不支援時，該服務無法連線， 平台端沒有任何設定可以補救。
    處理
    逐一盤點各服務實際使用的 driver 套件與版本，必要時請對方升級相依：
    • 已支援——libpq 17+（psql、psycopg）、pgx v5（Go）、node-postgres（Node.js）
    • 未支援——Rust 的 sqlx
    • 需依版本確認——pgjdbc（Java）、asyncpg（Python）
    另需涵蓋
    不是自家程式碼的 client 也要盤：BI 工具、GUI client（DBeaver、pgAdmin）、 Grafana datasource。這些內嵌的 driver 通常版本最舊，而且無法重新編譯或替換相依。
  3. P3

    憑證輪替後 Pooler 是否重新載入

    症狀
    cert-manager 更新 Secret 後，若 PgBouncer 未重新載入憑證，會在舊憑證到期時全面失效。CNPG 對使用者提供的 serverTLSSecret 更新後是否觸發 PgBouncer 重載，文件未明確說明。
    處理
    在續期流程後加入一次 Pooler rollout，並對憑證到期日設定告警。
  4. P4

    wildcard SAN 只涵蓋一層 label

    症狀
    *.db.example.com 對得上 tenant1.db.example.com，對不上 pooler.tenant1.db.example.com。client 使用 verify-full 時後者會驗證失敗。
    處理
    hostname 命名規則固定為單層，並在產生 TransportServer 的流程中強制。

部署時必須設定使用預設值會出問題

  1. P5

    Reload 的觸發來源與影響範圍

    症狀
    NGINX IC 每次套用資源變更都會重新產生設定並 reload，觸發來源不限於 TransportServer——該 controller 上任何 Ingress / VirtualServer 變動都會 reload。reload 後既有連線留在舊 worker，不會轉移到新 worker。
    處理
    為 DB 流量部署獨立的 NIC 實例（獨立 IngressClass 與 GlobalConfiguration），與 HTTP ingress 分離。
  2. P6

    worker-shutdown-timeout

    症狀
    reload 後舊 worker 在此時間到期被強制關閉，其上的既有連線一併中斷。ingress-nginx 預設 240s。
    處理
    調整為大於最長交易時間，並確認應用端連線池會偵測斷線並重連。批次套用 CR 以減少 reload 次數。
  3. P7

    三層 idle timeout

    症狀
    Cluster A nginx 的 proxy_timeout（預設 10m）、NIC 的 sessionParameters.timeout（預設 10m）、雲端 LB 的 idle timeout 任一先到期，連線都會被中斷。表現為連線看似存在，但下一個查詢無回應。
    處理
    三者都設為大於應用最長閒置時間，並在 client 連線字串加上 keepalives=1 keepalives_idle=30 keepalives_interval=10。
  4. P8

    passthrough 功能掛在 443 上

    症狀
    passthrough 不是另開一個 port，而是接管既有的 443。啟用 -enable-tls-passthrough 後，443 先由 SNI 路由器處理：命中 TLS_PASSTHROUGH 的 TransportServer 就原樣轉走，沒命中才交回原本的 HTTPS 處理。結果是 PostgreSQL client 必須連 443，且既有 HTTPS 流量多經過一層比對。
    處理
    以 -tls-passthrough-port=5432 把 passthrough 監聽器移到獨立 port，443 維持原狀。另需在 controller 前的 Service（LoadBalancer / NodePort）加上 5432——該 Service 預設只開放 80 與 443，未加則流量到不了 pod。
  5. P9

    連線數上限

    症狀
    兩個上限會先後成為瓶頸：instances × max_client_conn 決定邊界要維持的並發 TCP session；instances × default_pool_size × (db, user) 組合數 若超過 PostgreSQL 的 max_connections 減去保留連線，後端會拒絕連線。
    處理
    先算過兩條式子。以 max_db_connections 設硬上限，避免 pooler 數量增加後累積超出。

需要知道的行為無法消除，影響運維方式

  1. P10

    Client 來源 IP 被改寫

    行為
    每一跳 L4 proxy 都是新的 TCP 連線，PostgreSQL 看到的 client_addr 是 pooler pod IP。pg_hba 的 IP 規則與來源 IP 稽核失效。PgBouncer 不支援 PROXY protocol，直通模式下也無法注入。
    影響
    身分識別改以 DB role 與 application_name 為準。需要追來源 IP 時，以 Cluster A nginx 的 $remote_addr、SNI hostname 與時間戳做關聯。註：只要經過 pooler，PostgreSQL 本來就看不到 client IP，跨叢集額外損失的是 PgBouncer log 中的那一層。
  2. P11

    邊界不具備 PostgreSQL 層可觀測性

    行為
    直通模式下邊界只轉送 bytes，log 只有 SNI、連線數與傳輸量。握手失敗的原因、認證錯誤、查詢層問題在邊界皆不可見。
    影響
    除錯需在 client 與 PgBouncer 兩端進行。建議開啟 PgBouncer 的 log_connections / log_disconnections，並保留邊界的 SNI access log 以便關聯。
  3. P12

    不相容 client 的錯誤訊息不具指向性

    行為
    未使用 direct TLS 的 client 得到的是 server closed the connection unexpectedly，訊息不指向 TLS 交涉方式。
    影響
    在對外文件中明確寫出必要的連線字串參數，並提供一則已知錯誤訊息的對照說明。
  4. P13

    wildcard 私鑰的存放位置

    行為
    直通模式由 PgBouncer 出示憑證，因此 wildcard 私鑰會掛進 CNPG namespace 的每一個 postgres 與 pooler pod。能讀取該 namespace Secret 或 exec 進 pod 的人皆可取得。
    影響
    收斂該 namespace 的 RBAC 與 exec 權限。若組織對私鑰存放位置有規範，需事先確認。
  5. P14

    (listener, host) 唯一性

    行為
    同一組 listener 與 host 在 NGINX IC 中必須全域唯一，重複時其中一份 CR 會被拒絕，且不一定有明顯的錯誤回饋。
    影響
    hostname 由 controller 或 template 從 Pooler 名稱推導，不由人工填寫。並監控 TransportServer 的狀態欄位。
  6. P15

    健康檢查只到 TCP 層

    行為
    maxFails / failTimeout 只判斷 TCP 是否連得上。PgBouncer 存活但後端 PostgreSQL 異常時，連線仍會被送入後才失敗。
    影響
    應用層探測需要 NGINX Plus 的 healthCheck，或在 pooler pod 上設定能執行實際查詢的 readiness probe。

§4 改用 Traefik 的差異

若把 Cluster B 邊界換成 Traefik 的 TCP router（終止 TLS），§3 的問題會有增有減。以下對照 P1–P15。

Traefik 實作了 PostgreSQL 的 STARTTLS 交涉：它讀取首包、辨識出 SSLRequest、回覆 S， 之後才進行 TLS 握手並取得 SNI。因此 client 端不需要 direct TLS，TLS 在邊界終止， 邊界到 Pooler 之間改為明文連線。

不再需要處理共 9 項

  1. P1
    PgBouncer 版本——握手與 ALPN 由 Traefik 負責，PgBouncer 不再參與 TLS 交涉，1.25 的版本要求消失。
  2. P2
    連線方的程式套件——client 使用一般的 sslmode=verify-full 即可，driver 版本不再是前提。這是差異最大的一項。
  3. P3
    憑證輪替——憑證移到邊界，Cluster 與 Pooler 不再持有，CNPG 的重載行為與此無關。
  4. P5
    reload 的觸發來源——Traefik 在 process 內更新路由表，不重新產生設定檔、不重啟 worker，既有 TCP 連線不受影響。
  5. P6
    worker-shutdown-timeout——沒有 worker 汰換的機制，此設定不存在。
  6. P8
    443 的佔用——Traefik 用獨立的 entrypoint 監聽 5432，不牽動既有的 HTTPS 服務。
  7. P11
    邊界可觀測性——邊界持有憑證，能記錄 SNI、TLS 版本、憑證錯誤與握手失敗原因，另有內建 metrics 與 dashboard。
  8. P12
    誤導的錯誤訊息——client 走一般交涉，失敗時得到的是正常的 TLS 或認證錯誤。
  9. P13
    私鑰掛進 CNPG namespace——私鑰只存在於 ingress 側（但這是換位置，不是消失，見下方 T5）。

維持不變共 6 項

  1. P4
    wildcard SAN 只涵蓋一層 label——憑證的比對規則與存放位置無關。
  2. P7
    三層 idle timeout——仍有 Cluster A nginx、Traefik entrypoint、雲端 LB 三層，只是中間那層改設定在 Traefik 的 entrypoint 上。
  3. P9
    連線數上限——PgBouncer 的兩條式子不變。
  4. P10
    client 來源 IP 被改寫——Traefik 雖然能對後端送 PROXY protocol，但 PgBouncer 不支援接收，因此這一項無法藉此解決。
  5. P14
    hostname 唯一性——多個 router 命中相同的 HostSNI 時，行為取決於 priority，仍須由產生流程保證唯一。
  6. P15
    健康檢查層級——Traefik 的 healthCheck 僅適用於 HTTP service，TCP service 依賴 Kubernetes endpoint 的就緒狀態，仍不做應用層探測。

新增的問題需另外處理

  1. T1

    邊界到 Pooler 之間為明文

    症狀
    TLS 在 Traefik 終止，之後到 pooler pod 的那一段不再加密。這是端到端加密被打斷的位置。
    處理
    最低限度以 NetworkPolicy 限制只有 Traefik 的 pod 能連到 pooler 的 Service。若已有 service mesh，讓該段走 mTLS。
  2. T2

    新增一個單點

    症狀
    Traefik 成為所有資料庫連線的必經路徑。它異常時，所有租戶的連線同時中斷。
    處理
    多副本部署、設定 PodDisruptionBudget 與資源保留，並納入既有的告警與值班範圍。升版流程要考慮既有連線的處理方式。
  3. T3

    與現有維運方式不同的元件

    症狀
    Traefik 的設定模型（EntryPoint / Router / Service / Middleware）與 nginx 不同，log 格式、除錯手法、常見故障模式都要重新累積。
    處理
    納入既有的部署與監控流程，並在導入初期保留可回到方案 A 的路徑——兩者的 client 連線字串中 hostname 與 port 相同，切換不需變更 client（但 sslnegotiation 參數需調整）。
  4. T4

    相依於 Traefik 對 PostgreSQL 協定的支援

    症狀
    STARTTLS 代答是 Traefik 自行實作的功能。PostgreSQL 協定若有變動，或該功能在未來版本行為改變，會直接影響連線。
    處理
    升版前確認 release note 中與 TCP router、PostgreSQL 相關的變更。固定 image tag，不使用浮動版本。
  5. T5

    私鑰改由 ingress 側持有

    症狀
    P13 的私鑰問題是轉移而非消除：wildcard 私鑰改為掛進 Traefik 的 pod。能讀取該 namespace Secret 或 exec 進 Traefik pod 的人皆可取得。
    處理
    收斂 ingress namespace 的 RBAC 與 exec 權限。若組織對私鑰存放位置有規範，需確認 ingress namespace 是否符合。
  6. T6

    若要同時提供直通，設定需維護兩套

    症狀
    Traefik 的 TCP router 兩種模式都支援，可用兩個 entrypoint（例如 5432 終止、5433 直通）同時服務。但這表示 IngressRouteTCP、對外文件與 client 連線字串都有兩種版本。
    處理
    僅在確實有端到端加密需求時才開第二條路徑，並明確定義哪些服務走哪一條。
