自建 pg-proxy 架構

在 Cluster B 放一個自己寫的 PostgreSQL 感知代理：代答 SSLRequest、終止 TLS、 依 SNI 查表後直接轉發到對應的 Pooler。client 端零改動，既有 ingress 設定不再隨 pooler 數量變動。

§1 架構

pg-proxy 是路徑上第一個需要看 TLS 內容的元件，因此由它負責整個交涉。

§2 連線流程

關鍵在第 3 與第 5 步：代答那一個 byte，之後 SNI 就自然到手。

一次連線的完整交涉 1. client → 建立明文 TCP
2. client → SSLRequest (8 bytes)
3. pg-proxy → 'S' (1 byte，代答)
4. client → ClientHello (SNI = tenant1.db.example.com)
5. pg-proxy → 用 wildcard 憑證握手，從握手取得 SNI
6. pg-proxy → 查表：tenant1.db.example.com → tenant1-pooler.cnpg.svc:5432
7. pg-proxy → 撥到後端，對後端重做一次標準 SSLRequest 交涉
8. pg-proxy → 雙向 io.Copy，直到任一端關閉

第 5 步是整個設計的支點。nginx 的困境是「想在握手之前偷看 SNI」，所以需要 ssl_preread， 也因此被 SSLRequest 卡住。pg-proxy 是握手的執行方，SNI 對它而言是握手的正常輸出—— 在 Go 裡連 tls.Config.GetCertificate 的回呼中就拿得到，可以在那裡直接拒絕未知的 hostname。

第 7 步是自建的第二個好處。因為程式是自己寫的，對後端可以走標準的 PostgreSQL TLS 流程， 而不是 direct TLS——所以 PgBouncer 不需要 1.25 以上的版本，也不會有 ALPN 的問題。

§3 為什麼放在 Cluster B

位置決定了要裝幾套、私鑰放哪、以及能不能用 k8s DNS。

  • 一套就夠。代答的元件放在被連的那一側只需要一份；放在連出去那一側，每多一個 client 叢集就要多裝一套，還要各自處理憑證。
  • 可以用 k8s DNS 直連 Pooler。pg-proxy 在 Cluster B 內，往後端就是 tenant1-pooler.cnpg.svc.cluster.local:5432——與你們同叢集時的連線方式完全相同，不需要再經過任何代理。
  • 能直接 watch Pooler CR。路由表的來源就在同一個叢集裡（見 §4）。放在 Cluster A 的話得另外想辦法同步。
  • 私鑰位置較合理。wildcard 私鑰留在資料庫側，而不是 pod 數量多、變動頻繁的應用服務叢集。
  • Cluster A 維持零租戶設定。那台 nginx 依舊只是把 5432 轉到 Cluster B 的入口，新增 pooler 時不用動。
與既有 ingress 的關係

pg-proxy 不需要取代 ingress。讓 ingress 做單一 port 的純 TCP 轉發到 pg-proxy 的 Service 即可—— 因為上面只有一條規則，新增 pooler 永遠不會改到 ingress 設定，也就不會觸發 reload。 對外的 port 與 LoadBalancer 管理沿用既有流程。

§4 路由表從哪裡來

建議直接 watch Pooler CR，新增 pooler 時不需要任何額外操作。

hostname 與後端的對應關係有兩種來源：

  • watch Pooler CR（建議）——在 Pooler 上加一個 annotation 標示對外 hostname， pg-proxy 透過 informer 監聽變更並更新記憶體中的路由表。新增 pooler 時只要建立 Pooler 本身， 不需要另外產生 TransportServer 或 IngressRouteTCP。
  • ConfigMap 靜態表——實作最簡單，但每次新增都要改一份設定並讓 pg-proxy 重讀。
pooler.yaml（節錄）annotation 標示 hostname
apiVersion: postgresql.cnpg.io/v1
kind: Pooler
metadata:
  name: tenant1-pooler
  namespace: cnpg
  annotations:
    pg-proxy.internal/hostname: tenant1.db.example.com
spec:
  cluster:
    name: tenant1-db
  instances: 3
  type: rw

因為路由表由程式維護，可以在寫入時就檢查唯一性——同一個 hostname 被兩個 Pooler 宣告時直接拒絕並發出事件， 不會像 ingress CR 那樣靜默失敗。hostname 也可以由 Pooler 名稱自動推導，並強制單層 label （wildcard 憑證只涵蓋一層，a.b.db.example.com 驗證會失敗）。

§5 對後端的連線

這一段的選擇決定了 PgBouncer 的版本要求，以及內網是否加密。

pg-proxy 撥到 Pooler 之後有三種做法：

  • 標準 PostgreSQL TLS 交涉（建議）——送 SSLRequest、等 S、再握手。 PgBouncer 從很早的版本就支援這個流程，所以沒有 1.25 的版本要求。 憑證用 CNPG operator 自簽的內部 CA 驗證即可，wildcard 憑證不需要進到 Cluster。
  • 明文——實作最簡單，但需要 NetworkPolicy 限制只有 pg-proxy 能連 Pooler 的 Service。
  • direct TLS——沒有理由選這個，它只會多帶一個 PgBouncer ≥ 1.25 的要求。
憑證的分工

選第一種的話，兩段憑證是分開的：對外用 wildcard 憑證，只存在於 pg-proxy； 對內用 CNPG 自己管理的內部 CA，Cluster 完全不需要設定 serverTLSSecret。 這是所有方案裡憑證分工最乾淨的一種。

§6 需要自己處理的事

核心邏輯很短，能不能上線取決於這些周邊。

  1. 01
    Graceful shutdown 部署或重啟時不能直接砍掉所有連線。收到 SIGTERM 後停止接受新連線、等既有連線自然結束，並設一個上限時間。terminationGracePeriodSeconds 要配合調大。
  2. 02
    憑證熱重載 cert-manager 續期後要能在不重啟的情況下換上新憑證。用 tls.Config.GetCertificate 每次握手時讀取當前憑證，搭配檔案監看或定期重讀。
  3. 03
    連線上限與資源保護 每條連線佔兩個 socket 與兩個 goroutine。需要有全域上限、每個租戶的上限，以及超限時明確的拒絕行為，避免單一租戶耗盡整個 proxy。
  4. 04
    路由表的併發更新 informer 更新路由表的同時會有連線正在查表。用 atomic 換整份 map，不要就地修改。已建立的連線不受路由變更影響（它已經綁定後端）。
  5. 05
    後端故障與 timeout 後端連不上、握手失敗、閒置過久各自要有明確處理與回報。閒置 timeout 要與 Cluster A 的 nginx 及雲端 LB 對齊，避免互踢。
  6. 06
    可觀測性 至少要有：每個 hostname 的連線數與錯誤數、握手失敗原因、後端連線延遲。這是自建相對於第三方元件的優勢，但要自己實作。
  7. 07
    多副本 每條連線各自獨立、不共享狀態，所以可以水平擴充。Service 用一般的 ClusterIP 即可，不需要 session affinity。
  8. 08
    來源 IP 仍然會被改寫 這一項無法靠自建解決：PgBouncer 不支援 PROXY protocol，所以 PostgreSQL 看到的仍是 pooler pod 的 IP。可以在 pg-proxy 的 log 中記錄真實 client IP 與 hostname 做關聯。
實作規模

核心邏輯（代答、握手、查表、雙向 copy）大約兩百行。加上以上八項與測試，實際約 500–800 行。 這是你完全掌握的程式碼，代價是它的正確性與維護也完全由你負責。
