pg-proxy 權限控制與 SQL 稽核

單一叢集，路徑為 client → APISIX → pg-proxy → 各租戶 Pooler。 要在 pg-proxy 上做到「隨時把某個帳號關掉」以及「誰在什麼時候執行了什麼 SQL」——兩件都做得到， 代價是 pg-proxy 不再是位元組管線，而是 PostgreSQL 協定解析器。 政策的事實來源是既有中央服務的資料庫，Redis 只是投影。分三版做，第一版完全不碰協定。

§0 先回答問題

兩個需求落在協定的不同層，成本差很多。

  • 關掉某個 user 的連線 — 便宜 TLS 握手完成後、client 送的第一個訊息就是 StartupMessage， 裡面明文帶著 user 與 database。解析這一個訊息就能做連線層的准入判斷， 之後仍然可以退回 io.Copy 的快路徑。要連「已經建立的連線」也一起砍掉， 只需要一張連線登記表——兩邊的 socket 本來就在 pg-proxy 手上。
  • 記錄每一筆 SQL — 可行，但改變架構 SQL 藏在 startup 之後的訊息流裡，要拿到它就必須持續做訊息框架解析， 快路徑就此消失——所以它被排在第三版，前兩版都還留著 io.Copy（見 §10）。而且 extended query protocol 把一句 SQL 拆成 Parse / Bind / Execute 三個訊息， 要還原「這次執行的是哪句 SQL」得在 proxy 內維護每條連線的 prepared statement 與 portal 對照表。 這是本文其餘篇幅在談的事。
  • 不會變成資料庫層的授權 pg-proxy 攔得住「連線」與「語句」，攔不住 row/column 層的權限。 PostgreSQL 自己的 GRANT / RLS 仍然是最後一道，不能因為有了 proxy 就放鬆。

§1 架構

資料面只多了兩條線：政策從上面進來，稽核事件從下面出去。

APISIX 這一跳

它只能是純 L4。PostgreSQL 的第一個封包是 SSLRequest 而不是 ClientHello， 所以 APISIX 一樣看不到 SNI，做不了租戶分流——stream route 只有一條，upstream 就是 pg-proxy。 需要確認的是它能不能把 PROXY protocol 送給 upstream；不能的話，pg-proxy 稽核到的 client_ip 會是 APISIX 的 pod IP。既然已經同叢集， 也可以評估讓 pg-proxy 直接掛 type: LoadBalancer，少一跳、少一組 idle timeout 要對齊， 真實來源 IP 也自然保住。

§2 一條連線的生命週期

兩個閘門、四個稽核取樣點，都落在同一條連線上。

改寫後的完整交涉 1. client → 明文 TCP，接著 SSLRequest (magic 80877103)
2. pg-proxy → 'S'，用 wildcard 憑證握手，從 SNI 取得 tenant
3. client → StartupMessage (無 type byte，只有 length + 參數對)
4. pg-proxy → 閘門 ①：查 (tenant, database, user)，不通過就回 ErrorResponse 28000 並關閉
5. pg-proxy → 撥後端、做標準 SSLRequest 交涉，把 StartupMessage 原樣轉過去
6. 雙向 ↔ 轉送 R / p 認證訊息，直到 AuthenticationOk
7. pg-proxy → 登記連線，輸出 connect 稽核事件（此時身分才可信）
8. 迴圈 ↔ 逐訊息解析兩個方向，閘門 ② + query 稽核事件
9. 任一端關閉或被政策砍掉 → 註銷登記，輸出 disconnect 事件

第 6 步是這份設計刻意保守的地方：pg-proxy 不做認證。 SCRAM-SHA-256 的四則訊息原封不動地來回轉送，密碼與 verifier 都不進 proxy， 後端換密碼、改 auth_type 都與 proxy 無關。代價是第 4 步用的還是 client 宣稱的身分—— 真正可信的身分要到第 7 步才成立。所以閘門 ① 拒絕得早（省資源、錯誤訊息清楚）， 但稽核事件一律以第 7 步之後的身分為準。

兩個必須特別處理的 startup 變體

CancelRequest（magic 80877102）走一條全新的 TCP 連線， 沒有認證、沒有 user 欄位，只帶 PID 與 secret key。它不能走一般的 startup 路徑， 但因為 TLS 已經終止，SNI 仍然告訴你要轉給哪個 Pooler，轉過去讓 PgBouncer 處理即可。 多副本也沒問題——落在哪個 replica 都能轉。GSSENCRequest（80877104）回 'N' 拒絕， client 會退回一般流程。

§3 訊息解析要做到什麼程度

兩個方向的成本不對稱，不需要對稱地解析。

PostgreSQL v3 協定的每則訊息都是 1 byte type + 4 byte length + body （唯一的例外是 StartupMessage，它沒有 type byte）。 框架解析本身很便宜，貴的是「把 body 讀進記憶體」。所以規則是： 永遠解析 header，選擇性讀 body。

方向訊息要做什麼
C → SQ Query讀 body：這就是完整 SQL。閘門 ② + 稽核事件
C → SP Parse讀 body：記下 stmt 名稱 → SQL 文字。閘門 ② + 稽核
C → SB Bind讀 header 與前兩個字串：portal → stmt 對照。參數預設不讀
C → SE Execute讀 body：portal → stmt → SQL，這才是「執行」的時點
C → SC Close清掉對照表中的 stmt / portal
C → Sd CopyData只讀 header 直接串流，絕不進 buffer
C → SF FunctionCall記下 OID 即可，或直接視為不允許
S → CZ ReadyForQuery語句邊界：補上 duration、送出稽核事件
S → CC CommandComplete讀 body：UPDATE 3 這類 tag，帶影響列數
S → CE ErrorResponse讀 body：把 SQLSTATE 與訊息記進稽核事件
S → C其餘（T D S …）只讀 header，body 直接串流轉發
實作陷阱：type byte 會撞名

S 在 client→server 是 Sync，在 server→client 是 ParameterStatus； C 是 Close 對 CommandComplete； D 是 Describe 對 DataRow； E 是 Execute 對 ErrorResponse。 解碼器必須綁方向，兩個方向不能共用同一張表。

建議的基礎

不要自己寫編解碼。Go 的 github.com/jackc/pgx/v5/pgproto3 （或舊的 jackc/pgproto3/v2）已經把 frontend / backend 兩個方向的訊息定義完整實作了， 而且它就是 pgx 在用的那一份。唯一要留意的是它會把整則訊息讀進 buffer—— 對 CopyData 與超長 SQL 需要自己加一條只看 header 的原始快路徑， 不要讓 COPY 一個大檔就把 proxy 的記憶體吃光。

§4 存取控制

政策是宣告式的、共用的；「立刻關掉」是政策變更的副作用，不是一個 RPC。

政策必須是一份共用資源

pg-proxy 會有多個 replica，連線散落其上。如果「關掉 user」是打一支 admin API， 那支 API 只會打到一個 pod——這是最容易踩的坑。 政策必須是一份共用資源，所有 replica 看同一份： 寫入者只負責改那份資源，每個 replica 各自對手上的連線執行。 這一節先假設那份政策已經在每個 replica 的記憶體裡並描述執行行為； 它從哪裡來、由誰寫、多久更新一次，是 §5 的題目。

pg-proxy 看到的政策詳見 §5
# 一個 cluster 一個 HASH，field 是帳號，value 是它能連的 database
pgproxy:policy:tenant1    HASH
    app_rw         ["orders"]
    analyst_ro     []          # 空清單 = 關掉這個帳號
    __ok           "2026-09-09T11:02:37Z"

這份政策由誰產生、怎麼寫進去見 §5。 「查不到這個帳號時預設拒絕」是刻意的選擇。允許清單會逼你在新增帳號時明確寫出來， 而阻擋清單只能擋住你想得到的人。若現況不允許一次收緊，可以先用 allow 起步、 但把稽核打開，等實際看到有哪些帳號在連再翻過來。

三個執行點

  • 新連線
    閘門 ①，在 StartupMessage 之後 比對 (hostname, database, user, 來源網段)。拒絕時回 ErrorResponse， severity FATAL、SQLSTATE 28000、訊息寫清楚原因，然後關閉連線。 不要靜默 RST——client 端會變成難以診斷的逾時。連線數超過 maxConnections 時用 53300。
  • 定期重驗
    掃描連線登記表 每 N 秒把登記表裡的連線批次拿去 Redis 重驗一次 → 對每條不再被允許的連線， 往 client 送 ErrorResponse severity FATAL / SQLSTATE 57P01 （terminating connection due to administrator command），再關掉兩邊 socket。 這是 PostgreSQL 自己 pg_terminate_backend 用的同一個代碼， client 端的驅動程式都認得，會走既有的重連或錯誤路徑。 既有連線的撤銷延遲就等於這個掃描間隔，10 秒是合理的起點。
  • 每則語句
    閘門 ②，可選 在 Q / P 進來時檢查連線上的撤銷旗標—— 成本是一次布林讀取，不查 Redis。 它的唯一作用是讓撤銷落在語句邊界，而不是在傳輸到一半時斷掉。 有了定期重驗之後這一項的價值不高，第三版再做也可以。
「把某個帳號關掉」實際發生什麼 t+0 → 有人在中央服務把 analyst_ro 關掉，DB 那一列變成 disabled
同時 → 中央服務對 Redis HSET 一個空清單 '[]'
立刻 → 新連線在閘門 ① 查 Redis 就被擋，回 FATAL 28000
≤10s → 各 replica 的定期重驗掃到 user=analyst_ro 的既有連線
同上 → 送 FATAL 57P01，關閉 client 與 backend 兩側 socket
同上 → 輸出 disconnect 稽核事件，reason: policy_revoked
總計 → 新連線立即被擋；既有連線最慢一個重驗間隔。 若中央服務那次 Redis 寫入失敗，就退化成等 reconciler 補正
要一起想的兩件事

後端連線也要收乾淨。砍掉 client 側之後，往 PgBouncer 的那條連線必須一起關， 否則會在 pool 裡留下孤兒。應用程式會重連。 大多數連線池吃到 FATAL 會立刻重試——閘門 ① 一定要同步做好， 否則會變成「砍掉→重連→再砍」的迴圈，稽核 log 會被灌爆。可以考慮對被拒絕的來源加一點退避。

§5 政策從哪裡來

中央服務同時寫 DB 與 Redis，reconciler 負責把雙寫的漏洞補起來。

中央服務在開通或停用帳號時，除了寫自己的資料庫，順手對 Redis 做一次 HSET—— 撤銷因此是即時的，沒有任何輪詢延遲。代價是雙寫： DB 寫成功而 Redis 寫失敗（網路抖、程式當在中間、有人直接改 DB 沒走服務）時兩邊就分岔了， 而且沒有東西會告訴你。

所以還是要有 reconciler，但它的角色變了：不是唯一寫入者，是安全網。 它定期用 DB 的內容全量比對 Redis 並補正差異，把雙寫失敗在一個週期內自動治好。 這個分工的規則要講死：DB 是事實來源，Redis 是它的攤平—— 只改 Redis 不改 DB 的東西，會在下一輪被 reconciler 還原。 這正是 break-glass 覆寫必須放在另一組沒人 reconcile 的 key 的原因。

reconciler 讀 DB 這一段，還是不要 SELECT 他們的原始表： 請對方建一個唯讀 view（例如 pg_proxy_access_v1），把那個 view 當成契約—— 欄位、語意、以及「要改它必須先通知你」都寫在裡面。 沒有這層 view，某天一次無害的欄位改名就會讓 reconciler 靜靜地開始補錯東西。

key 與 value 長什麼樣

pg-proxy 在這裡只需要回答一個問題：這個帳號能不能連這個 database。 所以資料形狀就照著這句話長——一個 cluster 一個 HASH，field 是帳號名稱， value 是它能連的 database 清單：

Redis一個 cluster 一個 key
pgproxy:policy:tenant1    HASH
    app_rw         ["orders"]
    analyst_ro     ["orders","reports"]
    batch_job      ["orders","logs"]
    __ok           "1"          # 見下一段，只有這一個不是帳號

pgproxy:policy:tenant2    HASH
    app_rw         ["billing"]              # 跟 tenant1 的 app_rw 無關
    ...

就這樣。帳號名稱就是連線字串裡的 user， 也就是 StartupMessage 裡送過來的那個字串，一字不差。 {cluster} 用你們自己的 cluster 識別字——pg-proxy 從 SNI 查路由表就有了， 中央服務用它本來就在用的那個 id 即可。

不需要按 cluster 切嗎？需要。同名帳號在不同 cluster 是不同的人 （tenant1 的 app_rw 跟 tenant2 的 app_rw 沒有關係）， 攤平成一個大 HASH 就會撞在一起。同一個 cluster 內帳號不重複，所以 field 不會衝突。

三個操作,就這三個

中央服務 開通 · HSET pgproxy:policy:tenant1 app_rw '["orders"]'
停用 · HSET pgproxy:policy:tenant1 app_rw '[]' （空清單 = 什麼都連不了）
改權限 · HSET pgproxy:policy:tenant1 app_rw '["orders","reports"]'
pg-proxy → HMGET pgproxy:policy:tenant1 __ok app_rw
← 清單裡有沒有 client 要連的那個 database，有就放行

三個操作都是同一行 HSET，中央服務不用分岔程式碼路徑。 停用寫空清單而不是 HDEL，是為了讓 nil 只剩一個意思（沒申請過）， 下一段就是在講這件事為什麼重要。

以後要加東西的話

如果之後想加連線數上限、來源網段之類的，把 value 從陣列換成 {"databases":["orders"],"maxConnections":40} 就好，key 的結構不用動。 現在不需要就先不要放——value 每條新連線都要解一次。

每條新連線查一次 Redis

連線路徑上就是一次 HMGET：一個 RTT 取回兩個欄位，判斷完就走。 同一條連線上還有 TLS 握手、後端撥號、SCRAM 往返——次毫秒的 Redis 查詢是雜訊。 連線建立的速率也不是問題：應用程式的連線池會把連線握著， 真正的尖峰是部署或擴容時的重連風暴，那個量級 Redis 完全吃得下。

直接查帶來的最大好處是把新鮮度變成免費的： 沒有記憶體快照要維護、沒有版本化與指標切換、沒有 pub/sub、 也不需要通知任何人。HSET 一回來，下一條新連線就看得到—— 不存在「快照還沒更新」這個狀態。

既有連線靠重驗，不靠政策差集

killExisting 一度看起來需要「整份政策在記憶體裡才能算差集」，其實不用。 你手上已經有連線登記表：每 N 秒把登記表裡的連線拿去 Redis 重驗一次， 不合格的就送 FATAL 57P01 砍掉。 幾千條連線用 pipeline 分批查，幾個 RTT 就結束。 這比維護政策差集更簡單——你不需要知道「政策改了什麼」， 只需要知道「我手上這些連線現在還合法嗎」。 代價很明確：既有連線的撤銷延遲 = 掃描間隔。10 秒是合理的起點。

但 Redis 現在在連線路徑上了

這是這個選擇唯一真正的代價，要用兩件事把它收掉：

  • 逾時必須很短，而且逾時的行為要明確 沒有逾時的話，Redis 一卡住，新連線就是無限期地掛在那裡——比拒絕還糟， 因為 client 端看到的是逾時而不是錯誤訊息。設一個緊的上限（例如 100ms）， 並且明確決定超時後怎麼辦。
  • 一份只在出錯時才用的回退快取 把每個 key 上次成功的答案留在記憶體裡，只有 Redis 逾時或報錯時才拿出來用， 並設一個存活上限（例如 5 分鐘），超過就進降級策略。 正常路徑一律走 Redis，所以不會有新鮮度問題； Redis 抖一下也不會變成全叢集的連線故障。這大概二十行， 跟「整份快照 + pub/sub」是完全不同量級的東西。

reconciler 要全量撈，不要用 updated_at 抓增量

reconciler 的工作是「找出 Redis 跟 DB 不一致的地方」，所以它必須看得到全貌。 用 WHERE updated_at > X 撈增量會漏掉兩種最重要的情況： 被 DELETE 的列（增量查詢裡完全不存在，於是 Redis 裡那筆授權永遠留著）， 以及從來沒寫進 Redis 的舊資料（它的 updated_at 很舊，永遠不會被撈到）。 政策資料通常只有幾千列，全量撈的成本可以忽略，別為了省它製造漏洞。 同時請對方用軟刪除——停用是 status = 'disabled' 留在表裡，不是把列刪掉； 這樣 reconciler 才有東西可以對應到 Redis 裡那個空清單。

__ok 是什麼，為什麼值得多一個 field

這是整個設計裡唯一一個「不是帳號」的 field，加它的理由只有一個： HGET 回 nil 的原因不只一種。 可能是這個人真的沒申請過，也可能是 Redis 被 flush 了、換了新實例、 或整個 HASH 被 maxmemory 淘汰掉。 如果 pg-proxy 把 nil 一律當成拒絕，第二種情況就是整個 cluster 的人一起連不上。

__ok 由 reconciler 在一次完整同步成功後寫入（值放版本號或時間戳都行）， 和帳號放在同一個 HASH——所以它跟資料同生共死：

  • __ok 在，帳號是 nil 這個人真的沒有授權。照 defaultAction 處理（建議 deny）。
  • __ok 不在 整個 HASH 沒了，這份資料不可信。絕對不能當成拒絕—— 改用回退快取（上次成功的答案）並告警。

順帶一個 Redis 設定要確認：maxmemory-policy 不能是 allkeys-lru。 跟一般快取共用實例的話，記憶體壓力下政策 key 會被默默淘汰。 用 volatile-lru 且這些 key 都不設 TTL，或乾脆用獨立的 Redis 實例或 DB index。

別讓自己開不了機

如果中央服務的資料庫本身也在這個 pg-proxy 後面， 就會變成 pg-proxy 要啟動得先問 pg-proxy。reconciler 連中央 DB 一定要走 xxx-pooler.cnpg.svc 或 Cluster 的 rw service 直連， 不能走對外的 hostname。這件事很容易在測試環境沒事、上線那天才炸。

緊急封鎖：先不要做

中央服務掛掉時想直接在 Redis 擋掉某個人，會踩到一個問題： reconciler 下一輪拿 DB 比對，發現 DB 說這人可以，就把你的封鎖還原了。 解法是另外一組 reconciler 不碰的 field（例如 o: 前綴）， 但那會讓所有 field 都得帶前綴、reconciler 多一條必須遵守的規則、查詢多一個欄位。 先不要做。需要緊急封鎖時，暫停 reconciler 再改 Redis 就好； 真的變成常態需求，再回來加這個前綴，那時 key 的結構也不用動。

稽核帶上 __ok 的值

__ok 反正每次查詢都會一起取回，把它的值（版本號或同步時間） 寫進稽核事件。「這個帳號在 11:02 還連得進來」就能對到當時 Redis 裡是哪一版資料， 而不是靠時間戳去猜同步延遲。成本是零。

要跟中央服務談定的四件事

  • Redis 的寫入契約 key 是 pgproxy:policy:{cluster}、field 是帳號名稱、 value 是 database 清單、停用寫 '[]' 不要 HDEL。 這是對方唯一需要實作的東西——開通、改權限、停用全都是同一行 HSET。 同時要講明：寫 Redis 失敗不必重試也不必回滾 DB，記個 log 就好，reconciler 會補。
  • 一個唯讀 view 當契約 reconciler 讀的那一份。欄位固定、語意寫清楚、要改先通知， 附帶一個唯讀的 DB 帳號只能 SELECT 那個 view。 這是把「共用資料庫」這個反模式變得可以維護的唯一辦法。
  • 停用是狀態，不是刪列 status = 'disabled' 留在表裡，附上原因與時間， 跟 Redis 裡那個空清單一一對應。 這同時解決了 reconciler 對不到刪除、以及稽核缺少停用理由兩個問題。
  • 那個 user 是人還是 PostgreSQL role 若是人，中間需要一張 人 → role 的對應表；若多人共用同一個 role， 「關掉某個人」在 proxy 這層做不到，得先把 role 拆開。 這一項最可能推翻排程，建議在寫第二版之前先確認。

§6 一個完整的例子

一個 cluster，兩個帳號，從 Redis 內容到把帳號關掉為止。

cluster tenant1，對外 tenant1.db.example.com， 後端 tenant1-pooler.cnpg.svc:5432。 裡面有兩個資料庫 orders、reports， 兩個帳號 app_rw（應用服務）與 analyst_ro（分析用）。

    return fallback(cluster, user, db)   // Redis 逾時：用上次成功的答案
}
if vals[0] == nil {
    return degraded()                     // __ok 不在：整個 HASH 沒了，不能當拒絕
}
if vals[1] == nil {
    return deny("28000", "no grant")      // 這個帳號真的沒申請過
}

var dbs []string
json.Unmarshal([]byte(vals[1].(string)), &dbs)
if !slices.Contains(dbs, db) {

}
return allow()
三個帳號走同一段程式 app_rw · orders → ["orders"] 有 → 放行
app_rw · reports → ["orders"] 沒有 → FATAL 28000 database not granted
intern · orders → field 是 nil，__ok 在 → FATAL 28000 no grant

放行之後才撥後端、轉送認證訊息；AuthenticationOk 一到就登記連線並輸出 connect 事件。

三、11:04 要把 analyst_ro 關掉

中央服務一次交易 + 一行 HSET
UPDATE grants SET status='disabled', updated_at=now()
 WHERE cluster='tenant1' AND role='analyst_ro';

HSET pgproxy:policy:tenant1 analyst_ro '[]'
# 空清單 = 什麼都連不了。這一行失敗也不用重試 —— reconciler 會補
接下來發生的事 11:04:12 · HSET 完成
11:04:12 · 新連線查到空清單 → FATAL 28000
11:04:19 · 重驗掃描（每 10 秒）掃到登記表裡 3 條 analyst_ro 連線
11:04:19 · 各送 FATAL 57P01，關閉 client 與 backend 兩側 socket
11:04:19 · 輸出 disconnect 事件 reason: policy_revoked
11:05:07 · reconciler 全量比對：DB 與 Redis 一致，只刷新 __ok
如果那行 HSET 剛好失敗了

DB 已經是 disabled，Redis 還是 ["orders","reports"]—— 帳號在 11:04:12 沒有被擋住。到 11:05:07 reconciler 全量比對時發現不一致， 把它改成 []，接著 11:05:1x 的重驗掃描把連線砍掉。 也就是說雙寫失敗的後果不是「撤銷失效」，只是「撤銷退化成輪詢延遲」—— 這正是留著 reconciler 的理由。

§7 SQL 稽核

難的不是記錄，是把 extended protocol 還原成「這次執行了哪一句」。

simple 與 extended 的差別

用 psql 打一句 SQL 走的是 simple query：一個 Q 訊息，SQL 就在裡面， 記錄它是 trivial 的。但幾乎所有應用程式驅動（JDBC、pgx、asyncpg、SQLAlchemy）用的都是 extended protocol：

一次 extended query 的訊息序列 C→S Parse stmt="s3" · SQL="UPDATE orders SET status=$1 WHERE id=$2"
C→S Bind portal="" · stmt="s3" · 參數值 （可能含 PII）
C→S Execute portal="" · ← 這裡沒有任何 SQL 文字
C→S Sync
S→C ParseComplete · BindComplete · CommandComplete "UPDATE 1"
S→C ReadyForQuery ← 語句邊界，在這裡送出稽核事件

所以 proxy 必須在每條連線上維護兩張小表：stmt 名稱 → SQL 文字 與 portal → stmt。Execute 進來時查表還原 SQL， Close 進來時清掉。更麻煩的是 client 可以重用 named statement， 一次 Parse 之後執行上千次——這正是稽核有價值的地方，但也表示這兩張表必須有大小上限， 否則一個惡意 client 用大量 named statement 就能撐爆 proxy 的記憶體。超過上限時的行為要先決定： 記「未知 SQL」而放行，或直接斷線。

一筆事件長什麼樣

稽核事件（stdout，一行一筆）event: query
{
  "ts": "2026-09-09T11:02:41.318Z",
  "event": "query",
  "conn_id": "01K5R7Q2XJ",        // 串起同一條連線的所有事件
  "tenant": "tenant1",
  "sni": "tenant1.db.example.com",
  "client_ip": "10.42.7.19",      // 需要 PROXY protocol 才是真的
  "user": "app_rw",              // AuthenticationOk 之後才可信
  "database": "orders",
  "application_name": "orders-api",  // client 自己填的，不可信
  "protocol": "extended",
  "policy_revision": "2026-09-09T10:58:02Z/48213",  // 當時生效的政策版本
  "stmt_name": "s3",
  "sql": "UPDATE orders SET status = $1 WHERE id = $2",
  "sql_sha256": "9f2c1a…",        // 方便聚合與比對
  "sql_truncated": false,
  "params": null,                 // 預設不記，見下
  "duration_ms": 4.2,
  "result": "UPDATE 1",
  "error": null
}

另外三種事件用同一個 conn_id 串起來： connect（含 TLS 版本、後端 Pooler、握手耗時）、 auth（成功或失敗，失敗時帶 SQLSTATE）、 disconnect（含 reason：client_close / backend_error / policy_revoked / idle_timeout， 以及這條連線總共跑了幾個語句）。有了 conn_id， 「某帳號今天做了什麼」是一次 group-by，不需要靠時間戳硬湊。

參數值預設不要記

Bind 的參數值裡什麼都有——身分證號、email、甚至被 UPDATE 進去的密碼雜湊。 把它記下來等於把資料庫內容複製一份到 log 系統，而 log 系統的存取控制通常比資料庫鬆。 預設關閉；真的需要時做成 per-policy 的開關，並且對已知的敏感欄位做遮蔽。 SQL 文字本身也要設長度上限（例如 4 KB）並標記 sql_truncated， 否則一個幾 MB 的 INSERT ... VALUES 會直接打穿 log pipeline。

為什麼在這裡記，比在 PostgreSQL 記好

CNPG 的 Pooler 是 PgBouncer。一旦 pool mode 是 transaction， PostgreSQL 看到的來源就是共用的 server connection—— log_statement 或 pgaudit 記下來的 user 與來源 IP 都不是真的發起者。 pg-proxy 站在 PgBouncer 前面，是這條路徑上最後一個還看得到「哪個 client、哪個帳號」的位置。 這是把稽核放在這裡的主要理由，不只是方便。

稽核管線壞掉的時候

這個問題要先決定，因為它會改變程式結構。事件送不出去（收集器掛了、磁碟滿了）時： 盡力而為——bounded queue，滿了就丟並累加一個 metric，資料庫流量不受影響； 或失敗即拒——記不下來就不讓語句過去，稽核完整但資料庫的可用性從此綁在 log pipeline 上。 預設用前者，把後者做成 per-policy 開關，讓真的有合規要求的租戶才付這個代價。

§8 這個設計看不到的東西

先寫清楚邊界，之後才不會有人以為「都被記下來了」。

  • 繞過 pg-proxy 的所有路徑 叢集內任何 pod 都可以直接連 tenant1-pooler.cnpg.svc 或 Cluster 的 rw service， kubectl exec 進 pod 開 psql 更是完全不經過 proxy。 沒有把這些路徑用 NetworkPolicy 封起來，稽核就只是「有禮貌的人會被記錄」。 CNPG operator 自己、備份 job、superuser 都要各自處理例外。
  • SQL 內部再產生的 SQL DO $$ ... $$、function / procedure body、trigger、 EXECUTE 動態語句——proxy 只看得到最外層那一句。 要看到裡面必須靠 pgaudit，那是資料庫端的事。
  • row / column 層的授權 閘門 ② 能看到語句文字，理論上可以做「唯讀模式」之類的分類， 但用字串或簡易 parser 判斷 SQL 是否為寫入操作非常脆弱，繞過方式太多。 真的需要唯讀，做法是後端給一個唯讀的 PostgreSQL role，讓資料庫去擋。
  • SCRAM channel binding TLS 在 proxy 終止、對後端重建，channel binding 的綁定值兩段不同。 client 若設 channel_binding=require 會失敗。預設值 prefer 沒問題， 但要先確認沒有團隊把它設成 require。
  • 效能：解析成本不是主要風險 每則訊息多一次 header 解析與一次 map 查詢，量級是微秒； 真正會咬人的是配置與複製——大 COPY、超長 SQL、 每則訊息都 allocate 一次的解碼器。設計對了成本可忽略，設計錯了會在 COPY 匯入時直接 OOM。壓測一定要包含 COPY 與大量 prepared statement 的情境。

§9 新增的實作項目

延續〈自建 pg-proxy 架構〉的 01–08，以下是這份設計多出來的。

  1. 09
    未知訊息型別的處理 協定會演進，client 也可能送出你沒實作的訊息。要先決定：未知 type 一律照 header 長度轉發（fail-open，相容但可能漏記），或直接斷線（fail-close，嚴格但脆弱）。建議 fail-open 並發 metric，讓你知道有東西沒被涵蓋。
  2. 10
    每條連線的狀態上限 stmt / portal 對照表、未完成的語句計時器都是 per-connection 記憶體。要有筆數與總位元組的上限，超過時的行為要明確，並且在連線關閉時確實釋放。
  3. 11
    稽核管線的背壓 bounded queue、丟棄計數、批次寫出、收集器不可用時的行為。不要讓 log 的寫入直接發生在轉送的 goroutine 上。
  4. 12
    Redis 查詢的逾時與降級 緊的逾時上限、逾時後的明確行為、只在出錯時使用的回退快取與它的存活上限、__ok 不存在時的降級策略。這幾項要一起設計，否則 Redis 抖一下就是全叢集的新連線故障。
  5. 13
    CancelRequest 與 GSSENCRequest 兩個 magic number 都要在 startup 階段辨識。cancel 依 SNI 轉發、不套用閘門（它沒有身分可查），但要記一筆稽核事件。GSS 直接回 'N'。
  6. 14
    真實 client IP 沒有 PROXY protocol，稽核裡的來源就是 APISIX 的 pod IP，「哪台機器連進來的」這個問題就答不了。先確認 APISIX 能不能對 stream upstream 帶 PROXY protocol；不行的話，這是把 pg-proxy 直接對外的最強理由。
  7. 15
    測試涵蓋的協定情境 simple query、extended with named statement、COPY FROM STDIN 大檔、pipeline 模式（多個 Sync 交錯）、query cancel、連線中途被政策砍掉、超長 SQL、二進位參數。這幾項是實際會壞的地方。

§10 三個版本

第一版不碰協定，第二版才是分水嶺——但第一版有三件事現在就要做對。

  • 第一版
    SNI 分流與轉發 就是〈自建 pg-proxy 架構〉那份設計：代答 SSLRequest、終止 TLS、 依 SNI 查表、雙向 io.Copy。零協定解析、零政策、零 Redis。 這一版要解決的是「連得上、不會斷」，把〈自建 pg-proxy 架構〉§6 的 01–08（graceful shutdown、憑證熱重載、 連線上限、後端故障處理、可觀測性）做紮實比什麼都重要。約 500–800 行。
  • 第二版
    權限管控 解析 StartupMessage、閘門 ①、撤銷掃描、 Redis 查詢與降級、定期重驗、reconciler，以及 connect / auth / disconnect 三種連線層稽核事件。 語句仍然走 io.Copy 快路徑——這一版還沒有訊息解析的風險。 做完就能回答「誰在什麼時候連了哪個資料庫」並且隨時把帳號關掉。 proxy 端約 400–600 行，reconciler 約 300–500 行； 中央服務那邊只多一行 HSET。
  • 第三版
    SQL 稽核 雙向框架解析、stmt / portal 對照、query 事件、COPY 與超長訊息的串流快路徑、 閘門 ②。§3 與 §7 講的東西都在這一版。 這才是真正改變 pg-proxy 性質的版本，前兩版都還保留快路徑。 風險最集中，建議先跑純側錄——只記錄、不介入，確認解析沒有跟不上或誤判之後再啟用閘門 ②。 約 800–1200 行。
第一版現在就要做對的三件事

不做的話第二版不是「加功能」，是重寫：

  1. 連線登記表。第一版拿它做 graceful drain（本來就得做）， 第二版直接拿同一張表做撤銷掃描。不要讓它到第二版才長出來。
  2. 轉發路徑留一個切換點。把 io.Copy 收在一個介面後面， 第三版要換成解析迴圈時，外圍的連線管理、逾時、關閉邏輯完全不用動。
  3. 解析 startup，但不做任何判斷。多寫大約 50 行， 取出 user 與 database 記一行 log，然後照樣 io.Copy。 你會拿到「實際上有哪些帳號在連哪個庫、從哪裡連」的真實清單—— 那正是第二版寫允許清單時最需要的東西，而且第一版不承擔任何風險。
總量與心理準備

三版加起來大約 2000–3000 行。真正的成本不在行數， 在於第三版的性質不同——協定解析器的錯誤會直接表現成「某個 client 的某種用法連不上」， 測試矩陣比第一版大得多。這是 §9 第 15 項要認真做的原因。

第二版開工前要先定案的事

  1. 中央服務那個 user 是人還是 PostgreSQL role——若是人，而且有多人共用同一個 role， 「關掉某個人」在 proxy 這層就做不到，必須先把 role 拆開。 這一項最可能推翻排程，建議在第一版還在寫的時候就去確認。
  2. 唯讀 view 誰來建——reconciler 讀的那一份。沒有這層契約， 直接讀對方的表遲早會被一次無害的重構打斷。同時談定停用要用 status 而不是刪列， 以及 Redis 那邊對應的是寫 '[]' 而不是 HDEL。
  3. 中央服務願不願意直接寫 Redis——願意的話新連線的撤銷是即時的， 對方的成本是一行 HSET；不願意的話就退回純 reconciler 輪詢， 撤銷延遲等於輪詢間隔。這決定 §5 的 key 契約要不要跟對方談。
  4. 既有連線的撤銷延遲可以接受多久——等於重驗掃描間隔。 10 秒是合理起點，要更短就是拿 Redis 查詢量去換。
  5. Redis 是共用還是專用——共用的話 maxmemory-policy 必須確認過， 政策 key 被 LRU 淘汰掉是會全體斷線的那種故障。
  6. 政策的預設值——defaultAction 一開始就 deny， 還是先 allow + 觀察模式跑一段時間再收緊？建議後者， 而且觀察期用的就是第一版那份 startup log。

第三版才需要回答的

  1. 稽核的強度——盡力而為（預設）還是失敗即拒？這決定事件輸出要不要走在轉送路徑上。
  2. Bind 參數要不要記——若要，遮蔽規則由誰定義、log 系統的存取控制夠不夠。

與版本無關、但越早確認越好

  1. APISIX 是否保留——同叢集之下它提供什麼？若只是為了走既有的對外 IP 流程， 那 PROXY protocol 能不能開就變成關鍵，否則真實來源 IP 會遺失， 第一版的 startup log 和第二版的稽核都會少掉最有用的一欄。
  2. NetworkPolicy——只要有人能繞過 pg-proxy 直連 Pooler，第二版和第三版都只是裝飾。 這件事跟第一版一起上線最省事。
